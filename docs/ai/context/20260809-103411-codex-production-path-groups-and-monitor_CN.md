# Codex 新生产路径分组与监控配置

## 背景与原因

此前“Codex新（生产路径1）”和“Codex新（生产路径2）”仅是同一 API Key 分组 `#13 Codex新（生产）` 下的两个上游账号。用户 API Key 页面按分组展示和选择，不按账号展示，因此下拉框中只会出现一个“Codex新（生产）”选项。

## 生产变更

- 保留原分组 `#13`，原地更名为“Codex新（生产路径1）”。已有 12 个 API Key 继续引用同一分组 ID，不改变其可用性、模型范围或计费口径。
- 新建公开标准分组 `#69 Codex新（生产路径2）`，复制路径 1 的 OpenAI 平台、`0.15x` 倍率、模型列表、权限和计费相关配置。
- 账号 `#1132 Codex新（生产路径1）` 仅绑定分组 `#13`；账号 `#1164 Codex新（生产路径2）` 从原分组解绑，仅绑定分组 `#69`。
- 两个分组均为 `active`、非专属、公开可选。路径 2 的排序位于路径 1 之后，用户 API Key 分组选择器会分别显示两项。
- 在同一事务中写入分组和账号分组变更的调度器 outbox 事件；重启应用容器后由调度器重新加载。PostgreSQL、Redis、数据卷和 Tunnel 未重建。

## `/monitor` 配置

- 新建监控 `#11 Codex新（生产路径1）` 与 `#12 Codex新（生产路径2）`。
- 两条监控均使用 OpenAI Responses 协议、`gpt-5.6-sol`、30 分钟检测间隔，并分别使用对应路径的独立上游凭证。
- 凭证只在服务端加密转换和存储，未输出、未写入仓库或本文档。

## 验证

- 应用容器重启后状态为 `running healthy`，`http://127.0.0.1:18082/health` 返回 `200 {"status":"ok"}`。
- 渠道监控调度器启动时已加载 12 条启用监控，其中包括新增的路径 1、路径 2 监控。
- 首次真实检测：路径 1 为 `operational`，延迟约 `2820ms`；路径 2 为 `degraded`，延迟约 `6419ms`，原因是响应超过慢响应阈值，但请求仍成功。
