## 高峰日为什么一天一千多刀

- 不是生图主导。`2026-07-13` 至 `2026-07-17` 的图片成本每天约 `0.995540` 到 `8.600000 USD`，占当天总成本约 `0.070%` 到 `0.699%`。
- 主因是大量 `/v1/responses` 文本/代码请求，且 `gpt-5.6-sol` 从 7 月 11 日后成为最大成本模型。
- 高峰日每天请求量是一万级：
  - `2026-07-13`: 10842 次，`1229.615128 USD`
  - `2026-07-14`: 11717 次，`1427.859181 USD`
  - `2026-07-15`: 11822 次，`1375.274740 USD`
  - `2026-07-16`: 12836 次，`1453.400372 USD`
  - `2026-07-17`: 8525 次，`943.899879 USD`
- 成本结构主要由输入 token、输出 token、cache read 成本构成。以高峰段看，cache read 和 input 成本占比很高，符合长上下文 Codex/Responses 使用特征。
- 单请求没有明显爆炸：
  - 7 月每天 `(request_id, api_key_id)` 重复计费对为 0。
  - 每天单请求组最大成本约 `1.25` 到 `3.68 USD`。
  - 每天 `>=5 USD` 的请求组为 0。
- 结论：从 `usage_logs` 的 token/cost 分布看，不像历史“把请求体字节当 token”导致单次几十/上百刀的错误，也不像生图费用算错导致千刀级消耗。它更像大量真实高强度文本/代码请求叠加出来的成本。
- 注意：这些高峰日没有匹配 `usage_facts`，说明发生在 durable fact 扣费链路启用前或未 fact 化阶段；它们可用于成本/行为分析，但不能证明当时已按现在链路真实扣费。

## 50% 收益率公式

成本单价：

```text
12 RMB / 150 USD = 0.08 RMB/USD
```

单用户满额使用的月成本：

```text
月成本 = 日额度USD * 30 * 0.08 = 日额度USD * 2.4
```

50% 毛利要求：

```text
月价 >= 月成本 / (1 - 0.5) = 日额度USD * 4.8
```

如果固定当前月价，反推 50% 毛利下最大日额度：

```text
最大日额度USD = 月价RMB / 4.8
```

## 当前判断

- 7 月千刀级日消耗主要是用户数量增长后，真实高强度 `/v1/responses` 文本/代码请求叠加，不是生图错误主导。
- 当前低价高额度模型只在“用户平均远低于额度”时短期可跑；人数继续增长后，极易被少量高强度用户打穿利润。
- 要做稳定 50% 收益率，必须至少满足其中一个条件：
  - 用强硬日额度、并发和 RPM 把实际成本压在售价的一半以内。
  - 或者把套餐价格提高到 `日额度USD * 4.8` 附近。
- 后续改套餐时，建议同时设置：
  - 日硬 cap：达到额度立即阻断或顺延到次日债务。
  - 分组 RPM：避免脚本型高频请求把账号池瞬间打满。
  - 图片独立 cap 或更高倍率：虽然当前图片占比低，但图片成本波动和定价感知需要单独控制。
