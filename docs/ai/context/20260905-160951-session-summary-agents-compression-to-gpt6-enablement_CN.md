### 未做——这是最大的一块

**87 个真实客户邮箱仍公开在仓库里**（扫描于 16:05）：

| | 数量 |
| --- | --- |
| 被跟踪的 `docs/ai/context/` 文档 | 356 |
| 含真实邮箱的文档 | 92 |
| **去重邮箱数** | **87** |

邮箱不是孤立的——同目录下 210 个文档含「余额」、108 个含「订单」、71 个含「退款」、
59 个含 `usage_logs`、40 个含 `payment_audit_logs`。实际形态是
「为 `<邮箱>` 增加 5 美元余额，变更前 `0.00000000`，变更后 `5.00000000`」，
**邮箱 + 余额 + 金额直接绑定**。

1. **在 git 历史里，删文件没用。** 任何 commit SHA 都能取回。要真清除需 `git filter-repo` 重写历史 + 强推。

3. 本次**只防住新增值**，历史数据一条未清理——那属于是否重写历史的决策，未单方面执行。

### 结果

`gpt-6-astra` 已可用，实测计费**逐位正确**。截至 16:05 共 3 笔真实用量，偏差全部为 `0`：

| id | 用户 | 输入侧 tokens | `total_cost` | 偏差 |
| --- | --- | --- | --- | --- |
| 404479 | 真实用户 | 90,518 | `0.741284` | 0 |
| 404476 | 真实用户 | 8,344 | `0.017048` | 0 |
| 404425 | 管理员测试 | 8,352 | `0.017228` | 0 |

官方价 `$10 / $1 / $12.50 / $50` 每百万 token，`actual_cost = total_cost × 0.16 × 18` 全部吻合。

### 一个被推翻两次的判断

**第一次**：`20260905-131000` 记录「两个上游对 gpt-6 均返回 404，上游尚无此模型」。
实测发现那次测的是**裸 `gpt-6`**，而上游只认精确串 `gpt-6-astra`，一直是通的。

**第二次**：PR #2 声称修好了 GPT-6 计费。29 个 agent 的对抗核查推翻——
取价三级中生产命中的是**第 ② 级远端目录**，而 #2 只改了第 ③ 级 `fallbackPrices`。
真正的缺陷是 `matchOpenAIModel` 末尾的 `DefaultTestModel`(`gpt-5.4`) 兜底，
会让别名按 `$2.5/$15` 结算（输入少收 4 倍、输出少收 3.33 倍）。已由 PR #5 修复。

> 但实测证明该缺陷**在这条链路上触发不了**——`gpt-6`/`gpt6`/`gpt-6-astra-high`
> 在上游就被 404 拦掉，产生不了可计费用量。

### 一个不用 SSH 的判定法（可复用）

判断生产是否加载了远端价格目录：模型广场 `/api/v1/model-plaza` 是**公开端点且暴露价格**。
挑「只在远端目录（231 键）、不在内嵌目录（198 键）、且源码无硬编码兜底」的模型，
生产能报出精确价格即证明目录已同步。

实测 `claude-fable-5`、`claude-sonnet-5`、`gemini-3.5-flash-lite` 三个模型的
广场价与远端目录**比值均为 1.0**。

## 5. CI/CD

### 已建立

`.github/workflows/build.yml`：push 到 main 构建并推送
`ghcr.io/cnyui/sub2api:sha-<commit>` 与 `:main`。**实际跑通过**，
镜像 digest `sha256:e84e84b6...`。

刻意不产出 `:latest`——该 tag 归既有 `release.yml` 所有，两条流水线抢同一个可变 tag
会让「服务器拉到的是哪次构建」无法判定。

`deploy` job 改为 push 到 main 自动执行，但**缺 secrets 时优雅跳过**而非让流水线标红。
新增 `deploy/vps-deploy.sh.example`：含健康检查轮询、失败打日志给回滚提示、
以及**部署后自检 `BILLING_FINAL_MULTIPLIER` 是否真进了容器**。

### 仍缺（只有管理员能做）

- 5 个 `VPS_*` secrets（当前 `total_count: 0`）
- VPS 上的 `deploy.sh`

**所以自动部署链路仍未打通，第 2 节那些 PR 全部躺在 main 上没跑。**

### 一个原方案没察觉的坑

## 6. 全量定价审计的两个发现（**均未修复**）

### ① `gpt-5.6-sol` / `gpt-5.6` 在向用户超收

按 OpenAI **2026-08-24 降价前的旧价**计费：

| 维度 | 系统实际收 | 官方现价 | 偏差 |
| --- | --- | --- | --- |
| 输入 | $5 / M | **$4 / M** | **+25%** |
| 缓存读 | $0.50 / M | **$0.40 / M** | **+25%** |
| 缓存写 | $6.25 / M | **$5 / M** | **+25%** |
| 输出 | $30 / M | **$20 / M** | **+50%** |

27 小时窗口内 551 笔、**超收 `$104.40`**，约 `$93/天`，单人最高 `$30.29`，
6 个在售 GPT 分组全量受影响。

三层取价同错，重新同步目录修不好；目录里裸 `gpt-5.6` 键的值反而正确，
但别名归一化在查价前就把它改写成 sol，导致正确记录永不可达。

**管理员决定：先自行核实官方价再改，历史超收不退、只修当下。**

### ② 长上下文计费一道都没打开——方向相反

`accounts.extra.openai_long_context_billing_enabled` 默认 false，
且 **OpenAI 网关是唯一默认关闭该计费的路径**（Claude/Gemini/Grok 不传该指针、默认开着）。
`>272K` 的 GPT 请求按短上下文单价收。

**与 ① 方向相反**：① 是多收用户的钱，② 是少收。
但「平台是否真的吃亏」取决于上游是否按 2x/1.5x 向本平台收费，**这一点未验证**。

配套事实：
- 超阈倍率是 **2x 输入、2x 缓存读、2x 缓存写、1.5x 输出**——**缓存同样翻倍**。
  对 Codex 长会话（大部分输入是缓存读），漏掉缓存会把主要成本项低估近一半。
- 边界是**严格大于** 272,000；广场 `tier_label` 写的「>=272K」是错的。
- 判定口径为 `输入 + 缓存写 + 缓存读` 三者之和，不是纯 input。
- 远端目录用 `*_above_272k_tokens` 表达，而 `LiteLLMRawEntry` 只声明 `long_context_*` tag，
  `encoding/json` **静默丢弃**未知字段，目录中 `long_context_*` 命中数为 **0**。
  **同步远端目录不能自动维持长上下文计价正确。**

### 关于「Codex 会不会超 272K」

会。网关对 Codex 原生路径**无任何 token 级截断**；
且 **remote compact 请求携带的是压缩前的完整上下文**，是整个会话里最大的那次请求，
恰恰最可能越过阈值。所以长上下文档位不是理论问题。
