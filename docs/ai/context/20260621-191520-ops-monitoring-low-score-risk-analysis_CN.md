# 运维监控健康分偏低与风险分析

## 背景

2026-06-21 根据 `/admin/ops` 截图和本机只读统计，分析当前运维监控健康分偏低、可优化点和危险点。

## 数据来源

- 截图时间：2026-06-21 19:09 左右，页面显示健康分 `63`、状态「风险」。
- 源码公式：`backend/internal/service/ops_health_score.go`。
- 只读 SQL 统计时间：2026-06-21 19:15 左右，窗口为最近 1 小时。

## 关键结论

- 健康分偏低的主因不是 CPU、内存、DB、Redis 或后台任务，而是成功请求的 TTFT 慢尾过高。
- 源码中健康分由业务健康 70% + 基础设施健康 30% 组成；业务健康由错误率 50% + TTFT 50% 组成。
- TTFT P99 评分规则是 `1s -> 100`、`3s -> 0` 线性扣分；当前 TTFT P99 远高于 3s，因此 TTFT 子项已经扣满。
- 截图中 SLA 为 `100%`、请求错误率 `0%`，上游错误率约 `0.41%`，这些不是主要扣分来源。
- 基础设施指标较健康：CPU 约 `2.3%`，内存约 `2.8%`，DB/Redis/协程/后台任务均正常。

## 只读统计摘要

- 最近 1 小时成功请求 `289`，失败请求 `0`，SLA `100%`。
- Token 数约 `2610.391 万`。
- 请求时长：P50 `9387ms`，P90 `29809ms`，P95 `39722ms`，P99 `118293ms`，Max `227519ms`。
- TTFT：P50 `2305ms`，P90 `5404ms`，P95 `7253ms`，P99 `26706ms`，Avg `3547ms`，Max `62938ms`。
- TTFT 样本 `289` 个，其中 `289` 个超过 `1s`，`92` 个超过 `3s`，`10` 个超过 `10s`，`2` 个超过 `30s`。
- 慢尾集中在 Sub2API 上游账号 `cliproxy-local-openai`：当前 Sub2API 层只有这 1 个可调度 OpenAI 上游账号，并发上限 `3`。
- 按模型看，`gpt-5.4` 的慢尾最明显：47 次请求，TTFT P90 `8609ms`，P99 `53118ms`，Max `62938ms`；`gpt-5.5` 236 次请求，TTFT P90 `4839ms`，P99 `15074ms`。
- 最近 1 小时有 2 条被恢复的上游错误：1 条 upstream `401`、1 条 upstream `429`；客户端最终状态为 `200`，说明重试/恢复生效，但上游账号池里仍存在凭证或限流风险信号。

## 可以优化的方向

- 优先排查 CLIProxyAPI 内部账号池：当前 Sub2API 只看到一个聚合上游，慢尾实际大概率来自 CLIProxyAPI 内部某些账号、地区、代理、会话或模型映射。
- 针对 `gpt-5.4` 单独看账号切换、TTFT EWMA、上游错误和代理路径；该模型的 P99 明显高于 `gpt-5.5`。
- 调整首 token 前的超时与逃逸策略：慢账号/慢会话在 TTFT EWMA 高于阈值时应更快从 sticky 中逃逸或临时降权。
- 控制并发与排队：Sub2API 当前上游并发上限为 `3`，长请求 Max 达 `227s`，会占住槽位；应确认 CLIProxyAPI 内部是否有足够并发容量，否则盲目加并发会放大慢尾。
- 把 429/529 单独作为容量风险看待：当前 upstream error rate 排除了 429/529，适合 SLA 口径，但容量预警不能忽略它们。
- 将慢请求明细按 `account/session/proxy/model` 聚合，形成“慢尾来源排行”，再决定是剔除账号、降低权重还是调整超时。

## 危险点

- Sub2API 层只有一个可调度 OpenAI 上游 `cliproxy-local-openai`。这符合“三项目串联方案 A”，但也意味着 Sub2API 层没有备用上游；CLIProxyAPI 自身异常时会成为单点。
- TTFT P99 超过 `26s`、请求时长 P99 超过 `118s`，即使请求最终成功，用户也会感知为卡死，容易触发客户端重试、重复请求和槽位占用。
- 上游 `401` 被恢复说明某个上游凭证/账号状态可能已失效或临界；如果恢复链路失败，可能迅速从“隐藏风险”变成用户可见错误。
- 上游 `429` 被恢复说明容量或限流已经出现；如果流量继续增加，当前 0% 请求错误率可能突然恶化。
- 仅看 SLA 会误判健康：当前 SLA 100%，但体验质量已经差；监控判断必须同时看 TTFT、请求时长和并发槽位。
