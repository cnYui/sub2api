# 运维监控优化优先级

## 背景

基于 2026-06-23 的 TTFT 与错误复核：CLIProxyAPI 内部账号池已由用户确认有多个健康账号，Sub2API 今日数据也没有显示大量 upstream 401。当前优化重点从“隔离大量坏账号”转为“治理 provider 502、TTFT 慢尾、监控定位粒度和峰值期容量”。

## 不建议作为当前 P0 的方向

- CPU、内存、DB、Redis：当前指标正常，不是健康分低和用户体验差的主因。
- 大量 upstream 401：今日真实 upstream 401 只有少量恢复事件，不是当前主线。
- 首次请求系统性超时：今天聚合账号首条请求未超过 8s，账号+模型首条无超过 15s，不像冷启动系统性问题。

## 优化方向

### P0：provider 502 根因治理

- 按 `model/requested_model/upstream_model/request_path/error_message/provider_error_code` 聚合 502。
- 区分真实上游 502、CLIProxyAPI 返回 503/502、未知模型/路由错误被包装成 502、连接超时。
- 对“当前模型列表之外”的请求在 Sub2API 入口提前返回清晰 400/404，不让它污染 provider 502 指标。
- 对真实上游 502 建立短窗口熔断和重试预算，避免同一问题账号/路由连续打爆。

### P0：超过 15s 的 TTFT 慢尾治理

- 15s 作为强动作阈值：触发逃逸、重试或账号/路由降权。
- 8s 作为弱动作阈值：记录、预警、EWMA 降权，不建议立即强制重试。
- 重点看 08:00-17:00 峰值时段，而不是只看全天平均。
- `gpt-5.5` 和 `gpt-5.4` 分开治理：`gpt-5.5` 今日超过 15s 数更多，`gpt-5.4` 仍有长尾但不是唯一来源。

### P1：补齐 CLIProxyAPI 内部观测维度

- 当前 Sub2API 只能看到 `cliproxy-local-openai` 聚合账号，无法定位 CLIProxyAPI 内部具体账号/代理/会话。
- 建议让 CLIProxyAPI 在响应头或错误元数据中安全透传内部路由标识，例如 hash 后的账号 id、代理 id、region、session id。
- Sub2API 只记录脱敏标识，不记录 refresh token、access token、完整账号名或敏感凭证。

### P1：容量与并发策略

- 不建议在慢尾未治理前盲目提升并发；长请求会占槽，提升并发可能放大上游压力。
- 先按模型和时间段统计并发占用、排队、TTFT、duration，再决定是否增加并发。
- 如果峰值时段 502/TTFT 同时升高，应优先做限流、降级或分模型容量隔离。

### P1：监控与告警口径

- SLA 继续排除业务限流，但 429/529/502 应独立作为容量和上游风险告警。
- 增加慢尾指标：`ttft_gt_8s_count`、`ttft_gt_15s_count`、`ttft_gt_15s_rate`、按模型/路由/内部账号排行。
- 告警建议：15s 慢尾率超过 1% 持续 10 分钟为 P1；provider 502 率超过 2% 持续 5 分钟为 P0/P1，具体阈值按业务容忍度调整。

## 推荐落地顺序

1. 先做 502 分类和未知模型提前拦截，减少错误指标噪音。
2. 再做 TTFT `8s/15s` 分级治理，15s 强动作、8s 降权观测。
3. 然后补 CLIProxyAPI 内部脱敏路由标识，解决“知道慢但不知道谁慢”。
4. 最后再根据峰值期数据调整并发、排队和模型容量隔离。
