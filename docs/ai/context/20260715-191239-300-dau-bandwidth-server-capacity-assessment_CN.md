# 300 日活带宽与服务器容量初步评估

## 1. 目标与结论

目标是从当前约 35 个 API 日活用户增长到约 300 日活，按当前重度 Codex 使用行为近似为 10 倍业务负载。

采购建议基线：

- 带宽端口：最低 500 Mbps，推荐 1 Gbps
- 月流量：若双向计量至少 20 TB；若只计出站至少 15 TB
- 单机配置：最低 8 vCPU / 16 GB，推荐 16 vCPU / 32 GB
- 磁盘：最低 500 GB NVMe，推荐 1 TB NVMe，并配置独立备份
- 设计并发：至少 500 个同时在途 API 请求

当前最值得采购的是 `1 Gbps + 16 vCPU + 32 GB + 500 GB 至 1 TB NVMe` 的生产节点；月流量双向计量时 20 TB 只是下限，优先选择 30 TB，出站计量时优先选择 20 TB。若业务收入和可用性要求允许，最终应采用两个应用节点加独立 PostgreSQL，而不是继续把全部服务放在一台机器上。

服务器地区尚未确定。日本、香港、新加坡和美国西海岸的带宽价格、Cloudflare Tunnel 路径和 OpenAI 上游延迟差异很大，最终下单前必须从候选机房分别测试 Cloudflare、OpenAI 和中国主要运营商线路。本评估不绑定具体厂商或机房。

## 2. 当前事实基线

### 2.1 用户与 API 使用

北京时间 2026-07-15 快照：

- 当前 API 日活用户：35
- 最近 24 小时 API 活跃用户：41
- 单日成功落库请求：约 1.1 万
- 全历史单小时成功请求峰值：1,379
- 最近 7 天成功请求峰值并发：约 32
- 请求耗时 P50：10.7 秒
- 请求耗时 P95：54.6 秒
- 请求耗时 P99：299.4 秒

`usage_logs` 只包含成功落库的计费用量。失败请求，以及已知余额不足时未落库的成功上游用量，不在这些数字中，因此它们是可证明下限。

### 2.2 Nginx 用户侧响应流量

当前 access log 覆盖 2026-04-13 至 2026-07-15，共约 110 万条请求：

- 最近 24 小时响应正文：6.45 GB
- 最高单小时响应正文：2.05 GB
- 过去 30 天一分钟响应带宽 P95：1.40 Mbps
- 一分钟响应带宽 P99：2.57 Mbps
- 一分钟响应带宽 P99.9：4.84 Mbps
- 一分钟最大响应正文带宽：19.73 Mbps
- 五分钟最大平均响应正文带宽：7.10 Mbps

这里仅有 Nginx `$body_bytes_sent`，不包含请求体、HTTP/TLS/QUIC 开销、Cloudflare 与上游重试，也不包含 Sub2API 到 OpenAI 上游的流量。

### 2.3 服务器全链路流量

当前运行会话约 8 小时的观测：

- cloudflared 外部连接：约 8.75 GB 接收、2.54 GB 发送
- Sub2API 容器：约 11.3 GB 接收、12.1 GB 发送
- 30 秒容器增量采样：2.51 Mbps 接收、3.35 Mbps 发送，合计 5.86 Mbps

Sub2API 是模型中转服务，同一份数据会经过两条公网链路：

1. 用户 Prompt 经 Cloudflare 进入服务器。
2. 服务器把 Prompt 转发给 OpenAI 上游。
3. OpenAI 输出进入服务器。
4. 服务器再把输出经 Cloudflare 发给用户。

因此，单看 Nginx 返回给用户的响应正文会严重低估服务器实际网络流量。按容器和 Tunnel 计数交叉估算，当前业务节奏约为：

- 双向总流量：1.5-2.2 TB/月
- 可能计费的出站流量：0.8-1.3 TB/月
- 平均合计带宽：约 6-7 Mbps

这个范围已经排除了把 Token 直接换算字节的错误做法，但仍受请求压缩、内部 Docker 网络和短连接统计方式影响。采购时应使用上界并保留余量。

## 3. 300 日活容量模型

### 3.1 月流量

按当前用户行为线性增长 10 倍：

- 双向总流量：15-22 TB/月
- 出站流量：8-13 TB/月

再考虑用户行为差异、重试、软件更新、日志、备份和增长超预期，采购口径应为：

- 双向计量套餐：不少于 20 TB/月，推荐 30 TB/月或不限流量公平使用套餐
- 只计出站套餐：不少于 15 TB/月，推荐 20 TB/月

不建议购买 2-5 TB 月流量的普通 VPS。即使端口是 1 Gbps，也会先耗尽月流量配额。

### 3.2 峰值带宽

当前用户响应正文一分钟峰值约 20 Mbps，线性放大为约 200 Mbps。再叠加大 Prompt 上行、OpenAI 上游、协议开销和同时发生的多个长流，300 日活时合理峰值范围为 300-500 Mbps。

因此：

- 100 Mbps：不满足目标，平均负载可能可运行，但峰值会排队或丢包
- 500 Mbps：可用下限，余量有限
- 1 Gbps：推荐，能覆盖峰值、重试和继续增长

这里的 1 Gbps 是端口上限，不代表持续占满。月流量额度比端口标称值更容易成为真实限制。

### 3.3 并发

当前成功请求峰值并发约 32，10 倍后约 320。P99 请求持续约 5 分钟，上游慢首包还会制造更长尾部，因此不能只按平均 QPS 选型。

推荐按至少 500 个同时在途请求设计，并允许短时达到 800。该并发包括客户端连接、Nginx 到 Sub2API、Sub2API 到 CPA、CPA 到 OpenAI，以及数据库和 Redis 的控制操作。

## 4. 三档采购方案

### 方案 A：最低成本单机

- 8 vCPU
- 16 GB 内存
- 500 GB NVMe
- 1 Gbps 端口
- 双向 20 TB 或出站 15 TB/月

优点是成本最低、迁移简单。缺点是 300 日活时 CPU、内存和连接数余量有限，数据库、Redis、应用与代理互相争抢资源，任何硬件或系统故障都会全站中断。

该方案适合过渡，不建议作为稳定承载 300 日活的最终状态。

### 方案 B：高配单机，推荐起步

- 16 vCPU
- 32 GB 内存
- 500 GB 至 1 TB NVMe
- 1 Gbps 端口
- 双向至少 20 TB，推荐 30 TB；或出站至少 15 TB，推荐 20 TB/月
- 独立对象存储或异地服务器保存数据库备份

优点是采购和运维复杂度适中，足以覆盖 300 日活和约 500 并发的目标，并为日志、Docker、PostgreSQL 和连接池保留空间。缺点仍是单机故障域。

这是当前最合适的采购起点，但应预留增加第二应用节点的迁移路径。

### 方案 C：双应用节点加独立数据层

- 两台应用节点：每台 8-12 vCPU、16-32 GB、500 GB NVMe、1 Gbps
- PostgreSQL：独立 4-8 vCPU、16-32 GB、300 GB 以上 NVMe，或使用受管数据库
- Redis：与数据库隔离或使用受管服务
- 总流量额度不少于 20 TB/月，按节点分配时避免单节点套餐过小
- Cloudflare Load Balancer 或独立 Tunnel replica 做故障切换

优点是可滚动升级、单应用节点故障不会全站中断，数据库资源也不再受流式请求进程影响。缺点是成本和运维复杂度最高。

当 300 日活成为稳定规模、支付收入依赖站点连续运行时，应采用该方案。

## 5. 扩容前必须处理的瓶颈

单纯购买大服务器不能解决当前架构限制。以下事项应在大规模导流前完成：

1. CPA 当前按请求新建 Transport，连接不能复用，已有 FD 接近 256 的历史证据。必须改为共享连接池，并把进程 `nofile` 提高到至少 8192。
2. Nginx 当前只有一个 worker、1024 worker connections。500 并发时客户端和上游连接可能同时消耗两个连接，必须改为自动 worker 并把连接上限提高到至少 8192。
3. Sub2API 上游账号并发和 CLIProxyAPI 全局并发当前均为 100，300 日活推算峰值约 320，必须完成隔离压测后扩到至少 500，并保证上游 OAuth 池有对应容量。
4. 修复客户端断开后后台继续运行、首响应没有硬期限的问题，否则增长后长尾请求会持续占用连接、并发槽和费用。
5. 先落不可变 usage fact 和 durable outbox，避免高峰时内存队列或余额不足导致成功用量无法计费。
6. Nginx 增加结构化流量日志，至少记录 `$request_length`、`$body_bytes_sent`、请求耗时、上游耗时和关联 ID，并配置日志轮转。
7. PostgreSQL 建立自动备份和 PITR；Redis 明确持久化策略；所有服务配置自动重启和 readiness。
8. 当前宿主机数据盘曾达到 98% 使用，不能继续作为生产扩容基础。新服务器应设置 70%、80%、90% 分级磁盘告警。

## 6. 采购验收标准

下单前应确认服务商合同中的真实口径：

- 月流量是只计出站还是上下行合计
- 1 Gbps 是独享、共享还是突发端口
- 是否存在 95th percentile、每日限速或公平使用条款
- 超额后是限速、停机还是高额计费
- DDoS 清洗流量是否计入配额
- 国际线路到 Cloudflare 和 OpenAI 是否限速
- NVMe 是否有持续 IOPS 保证，快照和备份是否额外计费

技术验收应至少完成：

- 500 个长流并发压测，目标无 FD 耗尽、无账务丢失、无数据库连接池耗尽
- 300-500 Mbps 短时吞吐测试，目标无明显丢包和延迟突增
- 单应用进程重启、单节点故障和数据库恢复演练
- 连续 7 天记录真实入站、出站、P95/P99 带宽和每日流量，再校准月度配额

## 7. 最终建议

如果现在只买一台服务器，建议直接选择：

`16 vCPU / 32 GB / 500 GB-1 TB NVMe / 1 Gbps / 双向 20-30 TB 或出站 15-20 TB 每月`

不要为 300 日活购买 100 Mbps 或 2-5 TB 月流量的普通 VPS。也不要把“换大服务器”当作扩容完成：CPA 连接池、FD、Nginx connections、上游并发 100、取消传播和计费事实持久化必须先修，否则更大的机器仍会在用户增长时出现 524、连接耗尽和漏计费。
