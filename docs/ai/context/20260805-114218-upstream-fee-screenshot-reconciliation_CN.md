## 关键计算

### GLM

截图这条自身的算术是：

```text
62 × $1.40/M + 50 × $4.40/M = $0.0003068
$0.0003068 × 3.5 = $0.0010738 ≈ $0.001074
```

因此截图费用没有算错，但当前本地 GLM 已是 `1x`，本地 15 倍前为 `$0.0003068`，不会再等于截图费用。

### Kimi K2.6

按当前动态价格文件 `$0.954/M`、`$3.961/M`、`$0.161/M` 计算：

```text
55 × 0.954e-6 + 20 × 3.961e-6 + 3 × 0.161e-6
= $0.000132173
```

截图金额反推倍率为 `0.000465 / 0.000132173 = 3.518x`，考虑页面 token 与金额显示精度，基本是上游 `3.5x` 口径。当前本地 `1x` 的 15 倍前金额低于截图约 `$0.000332827`。

### Kimi K2.5 的额外价格源问题

当前动态价格文件把 K2.5 记为输入 `$0.60/M`、输出 `$2.25/M`、缓存 `$0.10/M`，所以本地按截图 token 得到 `$0.0000693`。但 `backend/internal/service/billing_service.go` 的硬编码 fallback 使用输入 `$0.60/M`、输出 `$3.00/M`、缓存 `$0.098/M`；按这组 fallback 价格并乘上上游 `3.5x`：

```text
55 × 0.60e-6 + 16 × 3.00e-6 + 3 × 0.098e-6 = $0.000081294
$0.000081294 × 3.5 = $0.000284529 ≈ $0.000285
```

这正好对应截图。说明 K2.5 不能只看倍率，还需要统一动态价格文件与 fallback 的价格来源；当前运行时优先使用动态价格文件，未直接修改，待单独确认价格口径后再处理。
