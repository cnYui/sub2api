# 同套餐续费与跨套餐购买拦截设计

时间：2026-07-15 09:32 JST

状态：设计已确认，尚未实施

## 背景

当前订阅购买校验只要发现用户存在任意有效订阅，就返回 `ACTIVE_SUBSCRIPTION_EXISTS`，导致用户无法提前续费当前套餐，并看到“需要先和管理员联系来进行退款”的提示。

现有履约层已经支持同一套餐组续期：`AssignOrExtendSubscription()` 会在用户存在相同 `group_id` 的未过期订阅时，从当前 `expires_at` 继续增加有效天数。因此根因不是缺少续期能力，而是购买入口的拦截粒度过粗。

## 业务定论

套餐购买和退款保持为两个独立流程，不互相调用或隐式联动。

1. 用户没有有效订阅时，可以购买任意在售套餐。
2. 用户已有有效订阅，购买相同 `group_id` 的套餐时，视为续费并允许支付。
3. 用户已有有效订阅，购买不同 `group_id` 的套餐时，直接拒绝创建订单，提示先退款当前套餐。
4. 退款完成并撤销原订阅后，用户恢复为无有效订阅状态，可以重新购买其他套餐。
5. 续费流程不发起退款、不计算退款金额、不修改退款状态，也不自动切换套餐。

“同套餐”以 `group_id` 判断，而不是 `plan_id`。实际订阅权益、API Key 分组和现有续期逻辑均以 `group_id` 为边界；`plan_id` 只是购买商品配置。

## 方案比较

### 方案一：按套餐组放行同套餐续费，跨套餐继续拦截

这是本次采用的方案。

- 优点：直接复用现有续期能力，不新增订阅状态或排队模型。
- 优点：购买与退款边界清晰，不产生自动补差、自动退款或套餐切换。
- 缺点：用户不能在原套餐有效期内预购其他套餐，这是确认后的业务约束。

### 方案二：不同套餐排队到原套餐到期后生效

需要新增待生效订阅、购买周期和取消规则，会把续费演变成套餐调度系统，不符合当前最简目标。

### 方案三：购买其他套餐时自动退款并立即切换

需要耦合支付、退款、权益撤销和新套餐履约，任一阶段失败都会形成跨状态补偿问题，明确不采用。

## 后端设计

将 `PaymentService.validateSubOrder()` 中的全局拦截改为目标套餐组感知校验，例如统一为：

```text
validateSubscriptionPurchase(userID, targetGroupID)

没有 active 订阅                 -> 允许
active.group_id == targetGroupID  -> 允许续费
active.group_id != targetGroupID  -> 拒绝
```

跨套餐冲突使用独立错误语义，例如：

- reason：`ACTIVE_SUBSCRIPTION_SWITCH_REQUIRES_REFUND`
- message：`当前套餐仍在有效期内，如需更换套餐，请先退款后再购买`

外部支付创建订单和余额支付必须复用同一个校验函数。余额支付必须在扣除余额、创建订单之前完成校验，保证冲突请求不扣款、不创建订单。

同套餐支付成功后继续调用现有 `AssignOrExtendSubscription()`：

- 复用原 `user_subscriptions` 记录，不创建第二条相同套餐权益。
- 从原 `expires_at` 增加本次购买的有效天数。
- 不重置当前日、周、月用量窗口。
- 支付订单关联原 `subscription_id`。

外部支付履约时保留后端最终校验，防止订单创建后、支付完成前用户订阅状态被管理员或其他入口修改。最终冲突只返回明确履约错误，不调用退款服务，也不自动切换权益。

本次不新增套餐排队、补差、自动升级、自动降级或自动退款状态。

## 前端设计

购买页把当前全局布尔判断改为针对目标 `plan.group_id` 的判断：

- 无有效订阅：套餐按钮显示“立即订阅”。
- 与当前有效订阅 `group_id` 相同：按钮显示“续费”，允许进入支付确认。
- 与当前有效订阅 `group_id` 不同：点击后显示跨套餐退款提示，不进入支付确认。

套餐卡片选择、续费弹窗选择和最终确认支付三个入口复用同一个前端判断函数。判断前继续强制刷新有效订阅缓存，后端作为最终权限边界。

前端不自动跳转退款页、不创建退款请求，也不根据退款状态推测是否允许购买；是否存在有效订阅仍以后端 active subscription 查询为准。

## 与退款逻辑的边界

本次不修改以下内容：

- 退款金额和自然日折算规则。
- Provider 退款状态机和重试资格。
- 退款成功后的订阅撤销事务。
- 共享订阅或续期后退款的 `MANUAL_REVIEW` 保护。

当前退款实现会在订阅已被续期、赠送或人工修改时转入 `MANUAL_REVIEW`，不会直接错误撤销整条权益。该行为继续独立存在，不纳入续费实现。

## 测试范围

后端测试：

1. 无有效订阅时允许购买任意套餐。
2. 有效订阅与目标 `group_id` 相同时允许创建支付宝订单。
3. 有效订阅与目标 `group_id` 相同时允许余额支付，并从原到期时间续期。
4. 有效订阅与目标 `group_id` 不同时返回新错误码。
5. 跨套餐余额支付不扣余额、不创建订单、不修改订阅。
6. 同套餐续费订单关联原 `subscription_id`，不新增第二条相同套餐订阅。

前端测试：

1. 当前套餐卡片显示“续费”并能进入支付确认。
2. 其他套餐点击后显示先退款提示，支付方法和确认页不打开。
3. stale active subscription 缓存会在判断前刷新。
4. 最终确认支付时再次执行相同套餐判断。

回归验证：

- 后端 payment/subscription 相关 unit 测试。
- 前端 `PaymentView` 与支付文案测试。
- 前端 typecheck、build。

## 非目标

- 不部署运行态。
- 不修改现有用户、订阅、订单或退款数据。
- 不允许不同套餐提前排队。
- 不支持自动补差升级或按剩余价值换套餐。
- 不重构退款业务逻辑。
