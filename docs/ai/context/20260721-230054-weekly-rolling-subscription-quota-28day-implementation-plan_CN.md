# 周滚动订阅额度与 28 天周期实施计划

## 依据与范围

本计划落实 `20260721-222923-weekly-rolling-subscription-quota-28day-design_CN.md`。目标仅为公共 Codex 订阅切换到“28 天有效期、每 7 天滚动刷新、尾窗按比例、额度展示整数、按额度比例退款”。不修改 CLIProxyAPI、Nginx、Cloudflare 或公网运行态，直到本地迁移演练和验收全部通过。

当前阶段只建立计划，不修改业务代码、数据库迁移或运行态数据。

## 阶段 0：建立迁移基线与阻断条件

状态：未开始。

1. 在本地附件数据库执行只读盘点，输出公共 Codex active 订阅、每条订阅剩余时长、待支付订单、退款中订单、完成订单缺少订阅链接、权益段重叠和无法归属的 usage facts。
2. 为每个异常对象生成可复核清单；异常对象不得被自动迁移或自动退款。
3. 确认两个历史超额账号的本地基线已经处理过，后续迁移仅写入 `already_applied` 审计事实，不再次扣减有效期。
4. 确认生产执行时必须重新读取和锁定生产数据，不能复用本地到期时间或本地扫描结果。

完成条件：得到可重复执行的 dry-run 报告，且每类异常都有“自动迁移、人工处理或阻断发布”的明确归类。

## 阶段 1：先实现向后兼容的数据模型

状态：未开始。

1. 新增前向迁移，扩展 `user_subscriptions`、`payment_orders`、`subscription_entitlement_periods`、`usage_facts`，并创建 `subscription_quota_debt_adjustments`。
2. 为订单写入版本化套餐快照；为权益段写入周额度、周期总额度和窗口规则；为 usage fact 写入权益段归属；为退款写入不可变计算依据。
3. 所有新增列先保持可空或带安全默认值，使旧应用版本仍可读取新 schema。
4. 更新 Ent schema、repository、DTO、迁移完整性测试和生成代码。

完成条件：现有日额度行为不变，新增 schema 可在空库和附件库成功迁移，且历史行可读取。

## 阶段 2：实现滚动周领域能力

状态：未开始。

1. 实现唯一的订阅滚动周窗口计算器：根据锚点、当前窗口、到期时间和当前时间计算窗口起止、有效周额度、剩余额度与重置时间。
2. 新购订阅以 `starts_at` 作为锚点；存量订阅以 `migration_at` 作为锚点；所有短窗按权益快照的周额度与实际时长比例计算。
3. 替换订阅路径中的自然周、自然日和旧日额度超额顺延逻辑；不修改用户平台 quota 的独立逻辑。
4. 统一请求前预授权、成功结算、DB 写入、Redis 缓存、L1 缓存、订阅进度和 Gateway 429 metadata 的窗口计算结果。

完成条件：同一订阅在缓存命中、DB fallback、结算和展示中得到相同的窗口、精确额度与 `window_resets_at`。

## 阶段 3：重构购买、履约和退款边界

状态：未开始。

1. 创建订单时锁定 plan/group 并写入套餐快照；支付履约、余额支付、补单和迟到回调只使用该快照发放权益。
2. 公共 Codex 新套餐统一为 28 天；套餐编辑、兑换码、默认注册订阅、认证来源赠送和管理员分配均显式传递期限与权益快照。
3. 实现退款 quote 和事务内二次计算：退款金额等于不含手续费购买本金减去已用额度比例对应价值。
4. 用 `entitlement_period_id` 汇总订单周期的 `usage_facts`；历史无法无歧义归属的用量阻断自动退款并转人工审核。
5. 退款仅撤销目标权益段，并重新计算订阅终止时间和窗口；保留后续续费权益。
6. 将管理员强制退款和按规则退款明确分流，并保留完整审计。

完成条件：计划在支付期间被编辑不会影响已创建订单；连续续费退款不会撤销后续权益；手续费不进入退款本金或网关退款额。

## 阶段 4：完成 API、用户页面和管理页面

状态：未开始。

1. 扩展订阅详情、订阅进度、Key 用量和 Dashboard API，返回精确窗口、有效额度、已用额度、剩余额度和重置时间。
2. 更新购买页和商品卡，删除日限额与 24 点刷新文案，展示套餐快照的周额度、28 天和购买时间起滚动刷新。
3. 更新订阅页、顶部订阅进度、Dashboard、Key 用量页：统一使用后端返回的有效额度和共享整数 formatter。
4. 更新用户订单退款弹窗，展示退款 quote；更新管理员订单和退款弹窗，展示订单快照、权益段、退款依据与强制退款审计。
5. 更新分组、套餐、订阅、系统默认订阅和认证来源默认订阅管理页面，以及中英文文案。

完成条件：所有用户可见额度都是四舍五入整数，但前端不参与限额计算；普通退款 UI 不允许手填绕过计算结果。

## 阶段 5：编写迁移工具并在本地演练

状态：未开始。

1. 编写可 dry-run 的存量迁移工具，输出逐订阅的旧值、锚点、首窗、有效额度、异常分类和将写入的权益快照。
2. 编写可 dry-run 的历史超额抵扣工具，使用 `floor(overage_usd / (72 / 7))` 计算天数，并以 `weekly_quota_cutover_overage:<subscription_id>` 保证幂等。
3. 对本地已处理的两条调整导入 `already_applied` 审计事实，不重复扣减；生产将重新扫描、锁定并应用。
4. 本地执行完整备份、迁移、缓存失效、验证与补偿 SQL 演练。

完成条件：dry-run 与正式执行输出可比对；重复执行不产生二次扣减、二次权益或二次退款。

## 阶段 6：历史超额账号门禁

状态：未开始。

1. 在完成前五个阶段并完成数据库迁移后，优先处理两个历史超额账号。
2. 在单一事务内写入债务审计、扣减订阅到期时间、截断覆盖新到期时间的 active entitlement periods，并失效 Redis/L1 缓存。
3. 验证订阅状态、权益段、精确周窗口与 Dashboard 一致；若订阅已过期，确认 API 请求被正确拒绝。
4. 未通过此门禁时，不运行购买、退款和整体回归测试。

完成条件：两条债务调整有唯一审计事实且订阅数据已回到周额度模型的正常范围。

## 阶段 7：测试与验收

状态：未开始。

1. 后端单元和集成测试覆盖新购四周、存量 1 至 6 天短窗、13 天存量、缓存一致性、成功结算和 429 重试时间。
2. 覆盖购买、余额/混合支付、支付回调重试、迟到回调、同组续费、不同组购买拦截、退款 quote、按规则退款、强制退款和多次续费退款。
3. 前端测试覆盖购买卡片、订阅页、Dashboard、Key 用量页、用户订单页和管理员退款页面；验证额度显示为整数而后端精确额度仍生效。
4. 运行 typecheck、lint、单元测试、集成测试和生产构建；在手机与桌面视口人工验收关键路径。

完成条件：设计文档列出的所有验收用例通过；无自然周、日限额或旧退款公式残留在公共 Codex 路径。

## 阶段 8：生产发布与回滚演练

状态：未开始。

1. 再次确认当前事实源、Nginx 指向、容器、volume、端口和可用磁盘空间。
2. 关闭公共 Codex 套餐售卖，处理旧待支付订单；完整备份 PostgreSQL 与 Redis，并验证 `pg_restore --list` 和 `redis-check-rdb`。
3. 部署向后兼容应用、执行前向迁移和存量迁移；发布期间阻断订阅购买、退款、管理员调整和公共 Codex 请求写入。
4. 先完成阶段 6 的超额账号门禁，再执行阶段 7 的生产验收样本，最后开放售卖。
5. 如需回滚，优先使用补偿 SQL 和缓存失效；只有停止所有写入后才允许整库恢复。

完成条件：健康检查、购买、模型请求、usage facts、退款 quote 和两个超额账号核验全部通过，且备份与回滚记录完整。

## 计划执行纪律

- 每个阶段开始前先更新本计划的状态与影响范围；阶段完成后把验证证据和未决问题记录到本计划。
- 不跳过阶段 0、5、6 和 8 的备份/门禁。
- 数据迁移、退款和超额抵扣必须使用事务、锁和幂等键；不能以手工 SQL 临时绕过。
- 发现历史数据无法无歧义归属时，停止该对象的自动处理并转人工审核，不为通过迁移而猜测数据。
