# 生图服务计费规则调研

## 调研范围

- 只读核对当前代码、运行态 PostgreSQL、项目模型价格文件和 OpenAI 官方文档。
- 数据库快照时间：`2026-07-16 14:15-14:22 +08`。
- 未修改业务代码、数据库、Redis、容器、配置或线上价格。

## 当前计费规则

当前并非按图片文件字节数收费，而是按输出尺寸归类后按张收费：

```text
图片费用 = 分辨率档位单价 × 实际生成张数 × 图片倍率
```

运行态所有允许生图的订阅分组均为：

| 档位 | 单张标准价 |
| --- | ---: |
| 1K | $0.10 |
| 2K | $0.20 |
| 4K | $0.40 |

代码会把最长边不超过 1024 归为 1K、不超过 2048 归为 2K，其余归为 4K；无法识别时默认 2K。只要请求成功生成图片且渠道不是显式 `token` 模式，计费就直接切换到图片路径，原请求的输入、缓存、文本输出和图片输出 Token 费用不再参与客户扣费。

因此当前真正的问题不是“按文件大小收费”，而是两个问题：

1. 使用分辨率档位作为客户价格规则，不能准确表达 `quality`、参考图和实际图片 Token 成本。
2. Responses API 调用图片工具时，主模型 Token 成本被图片固定价整体覆盖。

## 运行态数据

历史成功生图记录共 `216` 次请求、`304` 张图片，总标准价 `$54.101`，平均 `$0.177964/张`。其中 `46` 次请求一次返回多张图片，单次最多 `6` 张，因此计费单位不能定义为 HTTP 请求，必须定义为“实际完成的图片生成执行/输出图片”。

### 直接 GPT Image 2 请求

能观察到图片输出 Token 的 `81` 张图片分布如下：

| 指标 | 图片输出 Token/张 | 按 $30/百万 Token 的输出费用 |
| --- | ---: | ---: |
| P50 | 1,630 | $0.0489 |
| 平均 | 2,134.7 | $0.0640 |
| P90 | 3,945 | $0.1184 |
| 最大 | 5,488 | $0.1646 |

把全部输入 Token 都按较高的图片输入价 `$8/百万 Token` 保守估算后：

| 当前档位 | 样本 | 平均保守成本 | P90 | 最大 | 当前价格低于保守成本 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1K | 67 | $0.0659 | $0.1197 | $0.1235 | 11 次 |
| 2K | 14 | $0.0833 | $0.1396 | $0.1653 | 0 次 |

这说明当前 `$0.10` 的 1K 价格会在高 Token 图片上倒挂；`$0.20` 对目前直接接口样本足够，但不能覆盖任意高质量大图的理论成本。

### Responses 图片工具请求

OpenAI 官方说明：Responses API 使用图片生成工具时，主模型 Token 费用需要在图片生成费用之外另计。当前代码没有这么做。

按项目现有模型 Token 单价和长上下文倍率还原、但尚未叠加图片模型本身费用时：

| 主模型 | 主模型 Token 成本/张 P50 | P90 | 最大 | 当前图片价 |
| --- | ---: | ---: | ---: | ---: |
| gpt-5.5 | $0.0734 | $0.1604 | $0.6056 | $0.20 |
| gpt-5.6-sol | $0.1232 | $0.8716 | $3.3429 | $0.20 |
| gpt-5.6-terra | $0.5389 | $0.5389 | $0.5389 | $0.20 |

`gpt-5.6-sol` 的高成本来自大上下文和长上下文倍率。只设一个“全包固定图片价”无法合理覆盖这种跨度：若按最坏样本定价，普通用户会被严重高估；若按平均值定价，大上下文请求会持续倒挂。

## OpenAI 官方计费口径

截至本次调研，`gpt-image-2` 使用 Token 计费：

| Token 类型 | 输入 | 缓存输入 | 输出 |
| --- | ---: | ---: | ---: |
| 图片 Token | $8/百万 | $2/百万 | $30/百万 |
| 文本 Token | $5/百万 | $1.25/百万 | - |

官方计算器根据 `quality + width + height` 计算图片输出 Token。常用尺寸结果如下：

| 尺寸 | Low | Medium | High |
| --- | ---: | ---: | ---: |
| 1024x1024 | 196 / $0.006 | 1,756 / $0.053 | 7,024 / $0.211 |
| 1536x1024 | 158 / $0.005 | 1,372 / $0.041 | 5,488 / $0.165 |
| 2048x2048 | 397 / $0.012 | 3,568 / $0.107 | 14,272 / $0.428 |
| 2048x1152 | 157 / $0.005 | 1,413 / $0.042 | 5,650 / $0.170 |
| 3840x2160 | 371 / $0.011 | 3,336 / $0.100 | 13,342 / $0.400 |

在官方允许的尺寸约束内，理论最高输出约为 `2880x2880 high = 23,719 Token = $0.71157`。这还不包含提示词、参考图、主模型 Token 和服务利润。

官方资料：

- https://developers.openai.com/api/docs/guides/image-generation
- https://developers.openai.com/api/docs/pricing#image-generation
- https://developers.openai.com/api/docs/models/gpt-image-2

## 推荐计费规则

### 推荐方案：每次生图有最低调用费，Token 继续正常计费

不要再直接使用 `1K/2K/4K` 客户价格档位。建议统一为：

```text
请求总费用 = 主模型 Token 费用
          + max($0.30 × 实际完成图片数, 1.30 × 图片模型输入/输出 Token 标准成本)
```

规则说明：

- 每完成一次图片生成执行，最低收费 `$0.30`，与图片尺寸无直接关系。
- 一次 HTTP 请求生成 `n` 张图片，按 `n` 次收费，防止通过 `n>1` 绕过调用费。
- Responses API 的输入、缓存、输出、长上下文和 service tier 继续按现有主模型 Token 价格计算，不能被图片费用覆盖。
- 图片编辑的参考图输入 Token 和图片输出 Token 按 `gpt-image-2` 标准成本计算，并使用 `1.30` 成本系数；当实际 Token 成本较低时仍收最低调用费。
- 上游未返回图片 Token 时，先按 `$0.30 × 图片数` 兜底，并记录缺失指标；不能回退到尺寸档位。
- 没有产生最终图片的 4xx/审核拒绝/上游失败不收图片调用费；若 Responses 主模型已经产生可计量 Token，主模型 Token 仍正常计费。
- 流式 `partial_images` 会额外消耗图片输出 Token，应进入图片 Token 成本；官方说明每张 partial image 额外消耗 100 图片输出 Token。

选择 `$0.30` 的原因：

- 覆盖官方 `1024x1024 high` 约 `$0.211` 的图片输出成本，并为常见提示词成本和波动保留约 29% 空间。
- 高于当前直接接口样本最大保守成本 `$0.1653`，对现有常见请求有足够缓冲。
- 对 `2048x2048 high`、4K high 或其他高 Token 请求，不依赖固定价硬扛，`1.30 × 实际图片 Token 成本` 会自动抬升价格。

用户侧可展示为：

```text
生图 $0.30/张起；每次成功生成均收费，高 Token 图片和上下文按实际 Token 用量计费。
```

### 不推荐方案：一个全包固定价

如果业务强制要求“无论上下文、质量、尺寸都只收一个固定价”，则必须限制产品能力：

- 强制 `quality=medium`，图片费用可定 `$0.25/张`，但主模型 Token 仍应另计。
- 若允许 `high` 和全部合法尺寸，仅图片模型理论成本就可到 `$0.71157`，固定价至少应约 `$0.95/张` 才有约 25% 毛利空间，主模型 Token 仍应另计。
- 若连主模型 Token 也要包进固定价，运行态已有单张主模型 Token 成本 `$3.3429` 的样本，不存在兼顾普通请求与长上下文请求的合理统一价。

## 实施前必须补齐的计量

1. `usage_logs` 增加或可靠填充图片 `quality`、图片模型 ID、图片输入 Token、图片输出 Token和 partial image Token。
2. Responses 图片工具必须把主模型 Token 成本与图片模型成本拆开，不能二选一。
3. 计费单位使用完成的 `image_generation_call`/输出图片数，不使用 HTTP 请求数。
4. 图片 Token 缺失时使用固定最低价兜底，并增加缺失率监控。
5. 改价前用 shadow 方式同时计算旧价、新价和理论成本，至少观察 7 天后再切换。
