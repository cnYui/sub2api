# 441565547@qq.com 调用公网模型服务 413 排查

## 背景

- 用户：`441565547@qq.com`
- 现象：Codex Desktop 调用公网模型服务时返回 `413 Payload Too Large`，错误体包含 `BODY_TOO_LARGE` / `请求体过大`。
- 截图里的 URL 是 `https://aaccx.pw/responses`，不是 `https://aaccx.pw/v1/responses`。

## 排查结论

- 用户账号正常：`users.id=37`，状态 `active`。
- 用户 API Key 正常：`api_keys.id=44`，状态 `active`，绑定 `groups.id=3` / `codex-pool-29-usd`。
- 用户订阅正常：`user_subscriptions.id=55`，状态 `active`，有效期到 `2026-07-22 15:26:32 +08`，日限额 `29 USD`，当前日用量为 `0`。
- `usage_logs` 中没有该用户成功请求记录，说明这次失败没有进入 Sub2API 业务处理，也没有扣费。
- nginx access log 在 `2026-06-22 18:13` 前后多次记录：
  - `POST /responses HTTP/1.1` -> `413`，响应体长度 `56`，客户端为 Windows Codex Desktop。
  - 同时其他客户端大量 `POST /v1/responses` -> `200`。
- `https://aaccx.pw/responses` 小请求当前返回 yui.web 的 `404`。
- `http://127.0.0.1:18080/responses` 小请求返回 Sub2API 的认证错误，说明 Sub2API 本身支持裸 `/responses` 路由。

## 根因

`aaccx.pw` 的 nginx 只把 `/v1/*`、`/api/*` 和控制台 SPA 路由代理到 Sub2API，没有把裸 `/responses` 代理到 Sub2API。

因此用户把 Base URL 配成 `https://aaccx.pw` 时，Codex Desktop 会请求 `POST /responses`：

- 小请求落到 yui.web，返回 404。
- 大请求先被 `aaccx.pw` server 的 `client_max_body_size 100m` 拦截，返回 413。
- 请求没有进入 Sub2API，所以不是用户账号、订阅额度、模型池、CLIProxyAPI 或 Sub2API 计费逻辑的问题。

## 建议

短期建议用户把 Codex Base URL 改为下面之一：

- `https://api.aaccx.pw`
- `https://aaccx.pw/v1`

长期若要兼容 `https://aaccx.pw` 作为 Codex Base URL，需要在 `aaccx.pw` nginx server 中显式把裸 `/responses`、`/responses/*`、`/chat/completions`、`/embeddings` 等 Sub2API 已注册的无 `/v1` OpenAI 兼容别名转发到 `127.0.0.1:18080`。

本次只排查和记录，未修改 nginx、Sub2API、数据库、Key、订阅或计费逻辑。
