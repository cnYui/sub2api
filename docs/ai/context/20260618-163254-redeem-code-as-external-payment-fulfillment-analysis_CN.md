# 兑换码作为外部收款履约方式分析

## 问题

用户希望不启用 Sub2API 内置 Stripe / 支付宝 / 微信 / EasyPay 支付协议，改为用户下单后发放兑换码，由用户在 Sub2API 前台自行兑换。

## 当前代码能力

- Sub2API 已有兑换码系统。
- 管理员入口：`/admin/redeem`，支持批量生成兑换码。
- 用户入口：`/redeem`，用户输入兑换码后完成兑换。
- 兑换码类型包含：
  - `balance`
  - `concurrency`
  - `subscription`
  - `invitation`
- `subscription` 类型兑换码必须绑定订阅类型分组 `group_id`，并可设置 `validity_days`。
- 用户兑换 `subscription` 类型后，会刷新订阅状态。

## 判断

可以把兑换码作为“外部收款后的履约凭证”，从 Sub2API 角度绕开内置支付订单和 webhook 流程：

1. 管理员预生成或按订单生成订阅兑换码。
2. 用户在外部渠道付款。
3. 管理员或外部系统把兑换码发给用户。
4. 用户登录 Sub2API 后进入 `/redeem` 兑换。

但这不能消除支付合规和平台规则责任。只要存在用户付款，收款发生在哪个渠道，就要遵守哪个渠道的规则；兑换码只替代“Sub2API 内置支付履约”，不替代“支付本身”。

## 主要取舍

- 优点：
  - 不需要立即启用 Sub2API 内置支付。
  - 不需要处理支付 webhook、补单、支付服务商配置。
  - 当前代码已支持订阅兑换，MVP 成本低。

- 缺点：
  - 支付、发码、退款、对账需要人工或外部系统处理。
  - Sub2API `payment_orders` 不会记录这类收入，收入事实在外部。
  - 用户付款后未收到兑换码、兑换码被转发、退款后权益撤销等问题需要人工 SOP。
  - 如果使用个人转账或个人收款码进行经营性收款，仍可能触发平台风控、税务、消费者纠纷等风险。

## 推荐方向

MVP 可以采用“外部收款 + 一次性订阅兑换码”的方式，但不要把它理解为绕开支付规则；更准确的命名是“离线/外部收款履约”。建议每笔订单生成唯一兑换码，设置合理过期时间，在 notes 中记录脱敏订单号或手机号，并建立退款和补发流程。
