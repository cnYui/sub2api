# 961109198@qq.com Cloudflare 502 排查计划

## 背景

- 用户 `961109198@qq.com` 反馈大量 502。
- 截图时间显示 `20:41`，错误体为 Cloudflare `origin_bad_gateway`，不是 Sub2API 标准 JSON 错误体。
- 本轮目标是只读定位根因，不修改代码、不改数据库、不重启容器，除非后续明确需要。

## 必须区分的 502 类型

- Cloudflare `origin_bad_gateway`：Cloudflare 到源站链路、nginx 到应用 upstream、应用容器可达性问题。
- Sub2API 应用层 502：例如上游账号池不可用、`no available accounts`、上游模型返回 5xx、流式终止事件缺失等。
- 客户端重试后的聚合错误：`API call failed after 3 retries` 只说明客户端三次请求最终仍失败，不能直接代表同一个底层原因。

## 排查步骤

1. 固定运行态：确认 18084 应用容器、Postgres、Redis、nginx、Cloudflare 入口健康状态。
2. 固定用户身份：查询 `users`、active API Key、active subscription、group 绑定，确认是否存在 Key/订阅/额度类问题。
3. 对齐时间窗口：围绕 `2026-07-09 20:41 JST` 查询 nginx access/error log、容器日志、`ops_system_logs`、`usage_logs`。
4. 分类失败：按路径、模型、API Key、HTTP 状态、错误消息区分 Cloudflare 源站 502 与应用层 502。
5. 最小复核：只做安全的 health/API 状态读取，必要时用已有信息判断是否需要真实请求；默认不触发用户计费请求。
6. 记录结论：新增结果文档，并把可长期复用的定论写入 `AGENTS.md`。

## 初始假设

- 截图错误体高度符合 Cloudflare 源站错误，优先检查源站链路和 nginx upstream，而不是先怀疑用户 API Key、订阅或余额。
- 若同时间窗口 nginx 报 `connect() failed`、`upstream prematurely closed`、`upstream timed out`，则根因落在源站/应用容器链路。
- 若 nginx 到 18084 正常而应用日志出现 `no available accounts` 或上游 502，则是另一类应用层 502。
