# Kimi K3 上游原始价格与本地倍率关系核查

## 核查结论

用户 `1850226892@qq.com` 的 Kimi K3 请求（`usage_logs.id=287142`）没有从上游收到“已经计算好的金额”；上游响应只提供 token 用量，本地根据模型单价和倍率计算费用。

上游中转站的无成本探测接口 `/v1/sub2api/billing` 当前返回：

| 字段 | 值 |
| --- | ---: |
| `billing_scope` | `token` |
| `group_rate_multiplier` | `3.5` |
| `resolved_rate_multiplier` | `3.5` |
| `effective_rate_multiplier` | `3.5` |
| `peak_rate_enabled` | `false` |

该接口返回的是 Key 的计费倍率元数据，不是本次请求的已扣金额。

## 本次请求的三层金额

本地 Kimi K3 fallback 单价为输入 `$3/MToken`、输出 `$15/MToken`、缓存读取 `$0.30/MToken`。本次 token 用量得到基础成本：

`17230 × 3e-6 + 124 × 15e-6 + 256 × 0.30e-6 = 0.0536268`

按上游 Key 的 `3.5x` 推算，上游中转站原始调用价约为：

`0.0536268 × 3.5 = 0.1876938`

如果上游中转 token 与人民币按 `1:1` 结算，则可理解为约 `0.1876938` 个中转 token / 人民币等价额度。严格账单金额仍需上游提供余额或用量流水；当前探测接口本身不返回逐请求扣费。

本地实例按 `BILLING_FINAL_MULTIPLIER=15` 对上游价格口径放大：

`0.1876938 × 15 = 2.815407`

这与 `usage_logs.actual_cost=2.815407` 完全一致。

## 是否多乘了 3.5

按当前实现，`3.5` 没有乘在一个已经从上游返回的金额上，而是本地用来从 token 用量还原上游价格；因此当前公式：

`官方基础成本 × 上游/分组倍率 3.5 × 本地倍率 15`

等价于：

`上游原始价格 × 本地倍率 15`

不是：

`上游已经返回的 3.5 倍金额 × 本地又额外乘 3.5 × 15`

另外，`account_rate_multiplier=35` 只用于账号侧统计/配额口径，约等于 `3.5 × 10`，不参与用户余额扣费。该请求的账号侧成本口径为：

`0.0536268 × 35 = 1.876938`

## 只有在另一种业务口径下才需要去掉 3.5

如果“本地 15 倍”明确指的是“官方基础价格 × 15”，完全忽略上游的 `3.5x`，那么本次应扣：

`0.0536268 × 15 = 0.804402`

这会比当前扣费低 `3.5` 倍，但它不再是“上游原始价格 × 15”，而是“官方基础价格 × 15”。是否采用该口径，需要确认 15 倍的基准到底是官方基础价还是上游中转价。

本次只做核查，没有修改线上计费配置或余额数据。
