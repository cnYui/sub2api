## P0 复核结论

- P0-1 “隔离 CLIProxyAPI 内部坏账号”不再作为当前首要假设；用户已确认内部有多个健康账号，Sub2API 今日数据也没有显示大量被恢复的 upstream 401。
- P0-2 “首 token 超过 8-15s 的逃逸/重试保护”仍有价值，但今天更像尾延迟治理，不像账号首次请求系统性超时。当前建议把触发阈值分两级：超过 8s 记录并降权，超过 15s 才触发更强的逃逸或重试。
- P0-3 “确认 CLIProxyAPI 内部冗余”可降级；用户已确认内部账号状态正常。当前更需要盯 provider 502、峰值时段慢尾、以及 CLIProxyAPI 内部是否能把具体账号/代理维度暴露给 Sub2API 便于定位。

## 当前优先级建议

- P0：治理 provider 502 错误和超过 15s 的 TTFT 慢尾，避免用户体感卡死。
- P1：补充 CLIProxyAPI 内部账号/代理维度的慢尾观测，或把内部路由标识安全地透传到 Sub2API 监控字段。
- P1：保留 8s 阈值作为降权/预警，不建议仅因为偶发 8s 就强制重试，避免放大上游压力。
