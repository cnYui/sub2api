# 双 Sub2API 内层 100 并发设计

时间：2026-07-23 08:12

## 目标

将内层 latest Sub2API（`18086`）供外层 `18080` 使用的内部转发身份并发从 5 提升到 100。

外层继续是唯一公网入口、真实用户身份与计费事实源；内层继续只负责内部鉴权、账号调度和模型上游通讯。

## 现状与问题

当前链路为：

```text
公网用户 Key -> 18080 -> 内部固定转发 Key -> 18086 -> OpenAI OAuth 账号池
```

- 外层上游账号 `sub2api-latest-openai-upstream` 的并发为 100。
- 内层固定转发 Key 认证后对应的用户并发为 5。
- 内层有 22 个可调度 OpenAI OAuth 账号，账号级并发合计约 130。

因此，内层用户级并发 5 先于账号池生效，导致所有经 18080 转发的用户共享约 5 个并发槽，无法使用外层设定的 100 并发能力。

## 决策

仅修改 `18086` 内层固定转发 Key 所属用户的并发值：`5 -> 100`。

不调整以下配置：

- 外层真实用户的并发限制；
- 外层上游账号的并发 100；
- 内层 OpenAI OAuth 账号各自的并发、优先级和调度权重；
- 内层账号调度算法与会话粘性行为；
- 外层计费、套餐、流量卡和 `usage_facts` 逻辑。

## 设计理由

内层固定转发身份是所有外层请求的共同入口，适合承担“18080 到 18086”的总并发上限。把它设为 100 后：

- 端到端正常情况下的入口上限为 `min(外层账号 100, 内层转发身份 100, 可用内层账号容量)`，即最多 100；
- 单个 OAuth 账号仍受自身并发限制保护，不会因为入口放宽而被直接允许 100 个并发；
- 现有调度器仍会按会话粘性、账号优先级、负载率、等待数和最近使用时间选择账号；
- 某些账号被限流、禁用或不可用时，可用总并发会相应下降，这是上游保护的预期结果。

不采用“所有内层账号都改为 100”的方案。该方案会将账号池理论上限错误放大到约 2200，不能代表 OAuth 账号或 OpenAI 上游的真实承载能力。

## 职责边界

| 层级 | 身份与并发 | 负责内容 | 不负责内容 |
| --- | --- | --- | --- |
| 外层 `18080` | 真实用户 Key、用户并发、上游账号并发 100 | 公网鉴权、套餐/流量卡校验、计费、真实用户用量 | 内层 OAuth 账号管理 |
| 内层 `18086` | 固定转发身份并发 100、账号级并发 | 内部 Key 鉴权、账号调度、上游请求、账号限流保护 | 公网用户计费与真实用户身份识别 |

内层日志中出现的固定管理员用户/Key 用量仅是技术转发记录，不得作为公网用户账单依据。

## 变更与回滚

实施时仅通过内层管理面或受控数据库迁移更新该固定转发身份的 `concurrency` 字段为 100；不改动 API Key 值、账号凭证、分组绑定或运行容器网络。

回滚边界清晰：将同一字段恢复为 5 即可。回滚不会影响外层计费历史、已落库 usage 事实或内层账号状态。

## 验证标准

1. 读取内层管理面或数据库，确认固定转发身份并发为 100，内层账号级并发未变化。
2. 使用外层真实用户 Key 发起并发请求，验证超过 5 个且不超过 100 个请求可进入内层账号调度。
3. 确认外层请求仍以真实 `user_id` 与 `api_key_id` 生成并结算 usage fact。
4. 确认内层 usage log 仍只归属固定转发身份，且 `account_id` 分散到多个 OAuth 账号。
5. 在 101 个及以上持续并发请求下，预期由内层入口并发保护返回可识别的限流/并发错误；不得改写为错误的用户计费或上游成功记录。

## 范围外

- 本设计不改变公网入口、Nginx、Cloudflare Tunnel 或 Docker 网络拓扑。
- 本设计不扩大单个 OAuth 账号的并发额度。
- 本设计不处理账号池容量不足、上游账户限流或模型配额本身的问题。
