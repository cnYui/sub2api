# 负余额调用硬阻断与余额套餐欠费暂停设计

## 背景与根因

当前普通余额预检把 `余额 = 0`、低于保底金额的小额正余额和 `余额 < 0` 统一视为“普通余额不足”，随后允许 OpenAI 流量卡兜底。该判断同时存在于 API Key 认证中间件和网关计费二次预检。

因此，用户已经欠费时，只要流量卡剩余达到保底金额，仍会到达上游。若本次实际费用超过流量卡剩余，结算层为了保留已完成的业务事实，会把整笔费用继续记入普通余额，造成负余额持续扩大。

余额套餐首周到账已经采用“先偿还负余额，剩余部分才成为当前周套餐余额”的原子语义；缺口在于首周不足以还清欠费时，套餐仍保持 `active`，后续周额度会在到期后继续自动到账。

## 已确认业务规则

1. 所有需要计费执行的模型 API 请求，只要普通余额 `< 0` 就必须拒绝；流量卡和模型订阅都不能绕过欠费状态。
2. `/v1/usage`、`/v1/sub2api/billing` 和异步任务只读查询继续可用；网页登录、购买、退款等非模型调用不受影响。
3. 普通余额等于 `0` 时仍允许使用有效流量卡；低于保底金额的小额非负余额也可按现有流量卡规则兜底。
4. 没有有效余额套餐的欠费用户可以重新购买套餐，首周额度自动先抵扣欠费并写入还款账本。
5. 首周额度抵扣后余额仍 `< 0` 时，套餐进入明确的 `debt_paused` 状态；第二周及后续额度全部暂停，不因到达刷新日期而自动发放。
6. 暂停只能由管理员人工处理后恢复，不能因用户余额后来自动转正而自动恢复。

## 方案选择

采用显式生命周期状态 `debt_paused`。

不采用以下方案：

- `active + next_credit_at=NULL`：破坏“活动套餐仍有后续到账时间”的既有语义，且无法直接判断是欠费暂停还是脏数据。
- 定时任务每次发现负余额就跳过：缺少持久状态与审计，用户余额转正后会自动恢复，不符合“等待人工处理”。

`user_balance_packages.status` 当前为长度 20 的字符串字段，没有数据库枚举约束，因此新增状态不需要改变表结构；仍需要数据迁移处理上线时已经处于负余额的活动套餐。

## 调用资格设计

### API Key 认证入口

在非只读计费端点的 Key 状态检查之后、订阅或余额分支之前增加负余额硬阻断：

```text
balance < 0  -> 403 INSUFFICIENT_BALANCE
balance >= 0 -> 继续原有订阅、普通余额或流量卡判断
```

这层使用认证快照，负责尽早拒绝已知欠费请求。

### 网关二次预检

`BillingCacheService.CheckBillingEligibility` 从余额缓存或数据库读取最新余额，并在选择订阅模式、普通余额模式或流量卡兜底之前执行同一硬阻断。该层是最终入口边界，避免认证快照短暂陈旧时放行。

普通余额模式继续使用当前保底金额：非负余额低于保底值时，可以检查流量卡；负余额不调用流量卡检查器。

### 结算边界

上游调用前无法准确知道最终 token 费用，因此单个已经放行或并发在途请求仍可能在结算时首次形成负余额。结算层继续记录真实费用并失效余额缓存；从下一次二次预检开始必须拒绝。不得为了避免负数而丢弃已完成请求的费用事实。

## 套餐生命周期设计

### 首周到账

首周额度仍只发放一次：

```text
new_balance = balance_before + weekly_credit_usd
debt_repaid = min(abs(min(balance_before, 0)), weekly_credit_usd)
remaining_usd = weekly_credit_usd                         （balance_before >= 0）
remaining_usd = max(new_balance, 0)                       （balance_before < 0）
```

- `new_balance >= 0`：套餐按原规则进入 `active`（或单期套餐进入 `completed`）。
- `new_balance < 0`：套餐进入 `debt_paused`，`remaining_usd=0`，保留原计划 `next_credit_at` 作为审计和展示依据，但定时任务不得处理该状态。
- 继续写入 `balance_debt_ledger`，来源保持 `balance_package_initial_credit`。
- 新增订单审计 `BALANCE_PACKAGE_DEBT_PAUSED_{credited_count}`，记录暂停前后余额、周额度和原计划刷新时间。

### 运行中转入暂停

余额套餐定时服务每次启动和每分钟运行时，先扫描未到期、仍有后续期数的 `active` 套餐。若锁定用户后确认最新普通余额 `< 0`，则在事务内把套餐改为 `debt_paused` 并写入同类订单审计，不发放额度。

该扫描用于覆盖两类情况：

- 已上线历史数据中的负余额活动套餐；
- 套餐用户因某个已放行或并发在途请求首次形成负余额。

### 暂停期间

- 周刷新查询只处理 `active`，因此不会消费第二周或后续期数。
- `credited_count`、`next_credit_at` 和 `expires_at` 保持不变。
- 套餐有效期继续按原订单快照计算，不因欠费暂停而延长。
- 到达 `expires_at` 后正常转为 `expired`，清空 `next_credit_at`；未发放期数不补发。
- 退款报价和执行继续按订单及原总额度规则处理，`debt_paused` 不阻止退款。
- `debt_paused` 视为当前有效套餐，禁止同档续费和异档购买，返回明确的 `BALANCE_PACKAGE_DEBT_PAUSED`，避免用户付款但无法获得新首周额度。

### 管理员恢复

新增管理员接口：

```text
POST /api/v1/admin/payment/balance-packages/:id/resume-debt-paused
```

恢复事务要求：

- 套餐状态必须为 `debt_paused` 且尚未到期；
- 用户普通余额必须 `>= 0`，否则返回 `BALANCE_DEBT_OUTSTANDING`；
- 将状态改回 `active`，把 `next_credit_at` 设置为当前时间，使定时任务只发放一周额度并从恢复时间重新建立 7 天节奏；
- 不延长 `expires_at`，不修改订单状态或退款金额；
- 写入 `BALANCE_PACKAGE_DEBT_RESUMED_{credited_count}` 审计，记录管理员、恢复前余额和时间。

接口暂不增加新的管理员前端按钮；人工处理可通过管理员 API 完成，服务端保留完整校验和审计。

## 展示与购买行为

- 用户余额套餐接口把 `debt_paused` 纳入当前套餐查询，避免订阅页误显示“没有套餐”。
- 订阅页增加“欠费暂停”状态标签，并显示“首周额度不足以抵销欠费，后续额度已暂停，请联系管理员”。
- 暂停状态不显示为即将自动刷新；保留的 `next_credit_at` 仅标为“原计划刷新时间”。
- 购买接口在创建订单前和支付履约事务内都拒绝暂停套餐用户继续购买或续费。

## 上线数据处理

新增一次性迁移，选择以下记录并改为 `debt_paused`：

```text
user_balance_packages.status = active
users.balance < 0
credited_count < refresh_count
expires_at > now()
```

迁移不发放额度、不改变余额、订单、期数、刷新时间或有效期，并为每个订单写入幂等的暂停审计。运行时暂停扫描作为迁移后的持续防线。

## 测试与验收

采用测试驱动开发，至少覆盖：

1. 负余额且有足额流量卡时，API Key 认证返回 `403 INSUFFICIENT_BALANCE`，且不调用流量卡检查器。
2. 网关二次预检对负余额硬拒绝，包括流量卡和模型订阅场景。
3. 零余额加有效流量卡仍可用，避免破坏流量卡产品。
4. 新购套餐首周足够还债时正常激活；不足时余额保持负数、套餐进入 `debt_paused`、不生成套餐剩余。
5. 暂停套餐跨过多个刷新时间仍不增加 `credited_count`、余额和 `total_recharged`。
6. 活动套餐用户运行中变为负余额后，暂停扫描写入状态和唯一审计。
7. 暂停套餐仍可展示、退款和到期，但不能购买或续费。
8. 管理员无法恢复仍欠费或已过期套餐；余额非负时恢复成功且只重启一周刷新节奏。
9. 数据迁移只处理符合条件的记录，重复运行不重复写审计。

发布验收需运行后端针对性测试、相关 service/middleware/repository 回归、前端订阅页测试与类型检查，并在生产发布后验证健康检查、当前负余额用户全部无法调用、活动欠费套餐全部处于 `debt_paused`。
