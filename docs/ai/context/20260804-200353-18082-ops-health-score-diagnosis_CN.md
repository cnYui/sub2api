# 18082 运维健康分低分诊断

时间：2026-08-04 20:03 JST

## 结论

健康分低不是应用容器、数据库或 Redis 的资源瓶颈，而是两个公开 OpenAI 分组在上游拒绝后没有可用回退账号，叠加长上下文流式请求的首 token 延迟过高。

## 同一小时窗口证据

- 成功请求：82。
- 错误请求：448，其中 439 条是 `is_business_limited=true` 的路由阶段 503，9 条是计入 SLA 的上游错误。
- SLA：90.11%；错误率和上游错误率：9.89%。
- P99 请求时长：173,298 ms；P99 TTFT：59,654 ms。
- 应用、PostgreSQL、Redis 健康检查均正常，容器 CPU 分别约为 1.18%、0.77%、1.89%。

## 根因

1. 分组 9「GPT模型官方0.15倍价格」和分组 10「GPT模型官方0.35倍稳定」各只绑定一个 OpenAI 账号，且都未配置 `fallback_group_id`。
2. 两个账号分别收到上游 403 `Your request was blocked` / `Access forbidden`，系统按既有策略进入临时不可调度冷却。冷却期间调度器没有候选账号，返回本地 503 `Service temporarily unavailable`，形成 439 条业务限流记录。
3. 9 条实际错误为上游 403、502、503、524；它们进入 SLA 错误率，未被业务限流口径排除。
4. 成功流式请求也存在严重上游首包延迟。样本中 TTFT 达 69 秒，请求总时长最高约 179 秒；高缓存读取和长上下文请求占比较高，但这不能解释上游 403，二者是并存问题。

## 评分口径

健康分由业务健康 70% 和基础设施健康 30% 组成。业务健康中的错误率与 P99 TTFT 各占 50%；P99 TTFT 超过 3 秒即为 0 分。因此，基础设施满分也无法抵消约 10% 的上游错误率和约 60 秒的 P99 TTFT。

439 条业务限流不直接计入 SLA 错误率，但它们证明用户请求在渠道无可用账号时被拒绝，不能视为服务正常。

## 处置优先级

1. 先修复或替换被上游 403 拒绝的两个账号，确认来源 IP、凭证、渠道权限和上游风控状态；继续重试不会解决 403。
2. 为每个公开 GPT 分组至少配置一个独立健康的备用账号，或设置经验证兼容的回退分组，避免单账号冷却导致整个分组不可用。
3. 对高 TTFT 的长上下文流式请求单独观察，并按模型、账号和上下文长度设置并发/队列控制；在上游恢复前，降低长请求并发不能替代账号修复。
4. 监控页面应继续区分「业务限流」与「SLA 错误」；当前分数真实反映上游可用性退化，不能通过改评分阈值掩盖。
