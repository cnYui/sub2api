# 余额套餐周期与 18080 迁移核查

## 核查结论

- 余额套餐的业务口径是每 7 天到账一次，28 天共 4 次；¥49 套餐为 `$128/次`，完整周期上限为 `$512`，不是首日一次性到账 `$512`。
- 18082 运行库中确实存在生命周期元数据异常：`user_balance_packages.refresh_count` 出现 5、7、9、18、22、23、30 等值，`expires_at` 也存在 30 天至 210 天的历史周期。部分记录来自旧迁移脚本按历史结束时间向上取整的结果。
- 迁移余额没有把 28 天总额度一次性写入用户余额。离线 18080 备份与 18082 目标库对照：
  - `313398924@qq.com`：源当前周剩余 `$59.579662`，目标余额为 `$59.579662`。
  - `1850226892@qq.com`：源当前周剩余 `$0.955092075`；迁移后目标产生 `$2.815407` 实际用量，目标余额为 `-$1.86031492`，与 `0.955092075 - 2.815407` 一致。
  - `2894823499@qq.com`：源当前周剩余 `$82.2321212`，迁移后目标余额为 `$81.76923032`，差额对应迁移后新增用量。
- 因此不直接按套餐总额回收或重置现有用户余额；这样会把迁移后的真实使用、普通充值和返利混在一起，造成二次扣款。先修正生命周期，阻止未来超期或超次数到账。

## 修复内容

- 新增 199 号迁移：将订单快照和用户套餐记录对齐到套餐计划的 28 天/7 天/4 次，截断异常 `credited_count`，重算到期时间和下一次到账时间，并清理同一用户的旧有效记录。
- 定时到账查询和条件更新都要求套餐尚未过期，避免停机恢复后给已过期套餐补发。
- 周期到账审计动作按到账次数生成唯一名称，避免 `payment_audit_logs(order_id, action)` 唯一索引导致第二次刷新事务回滚。

## 部署后核验

部署后必须确认：

1. `schema_migrations` 已记录 `199_normalize_balance_package_lifecycle.sql`。
2. `user_balance_packages` 中所有非退款记录的 `refresh_count=4`、`refresh_interval_days=7`、`expires_at=starts_at+28 days`，且 `credited_count<=4`。
3. 18082 应用健康检查通过，迁移前后用户余额没有被批量重算；下一次周期到账审计动作应为 `BALANCE_PACKAGE_WEEKLY_CREDIT_2`、`_3` 或 `_4`。
