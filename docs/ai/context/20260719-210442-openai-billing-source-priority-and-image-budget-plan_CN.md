# OpenAI 计费来源顺序与图片预算修复计划

## 已确认规则

- OpenAI 模型请求的唯一来源顺序固定为：套餐额度 -> 流量卡额度 -> 402。
- `users.balance` 是账户资金，只用于购买、退款等资金业务，不参与模型请求预授权或结算。
- 单个请求只能使用一种来源；套餐不能完整覆盖保守预算时，整次请求才转流量卡，不跨来源拆分。
- 未显式指定最大输出 Token 时，可降低输出上限以使套餐优先通过；显式上限不得改写。
- 最终结算只能执行请求前确定的授权快照，不能根据实际费用重新选择来源。

## 根因

1. 预授权服务将余额作为无套餐时的候选来源，且套餐预算不足会直接进入流量卡，规则分散在请求前和结算后两处。
2. 套餐只有余额检查，没有 reservation，并发请求可穿透额度上限。
3. 图片请求的部分解析失败或 multipart 路径仍可能把传输字节当文本 Token；文本预算也使用字节近似值。
4. 流量卡结算日志沿用余额类型，导致审计和前端筛选失真。
5. 个别 OpenAI 入口和 CLIProxy usage event 未稳定继承原始授权，可能重新选源或重复落账。

## 实施步骤

1. 先增加失败测试，固化套餐优先、余额忽略、无套餐时流量卡、图片文件字节不计入文本预算、流量卡日志类型。
2. 为套餐新增事务 reservation 和迁移，授权结果携带来源专属 reservation；按“套餐 -> 流量卡”原子选择并在 shadow 模式只观测、不拒绝、不扣费。
3. 结算层只消费授权快照，补齐各 OpenAI HTTP/WebSocket/图片入口对授权生命周期的处理；无授权的 CLIProxy event 仅审计跳过。
4. 使用内嵌词表 tokenizer 估算 JSON 里的可计费文本；multipart 只传入语义字段，永不以请求体或文件长度估算 Token。
5. 新增 `BillingTypeTrafficCredit`，迁移历史上关联流量卡 ledger 的 usage log，并更新查询与展示筛选。
6. 运行服务层回归测试、迁移测试、前端类型检查和构建；完成后记录结果和未部署边界。

## 不在本次范围

- 不修改用户余额、历史套餐使用量或线上数据库。
- 不改变购买、退款、组合支付的余额语义。
- 不部署容器、不改 Redis、Nginx 或公网链路。
