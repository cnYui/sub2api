# OpenAI 外部中转 403 来源分析

时间：2026-08-04 20:03 JST

## 可确认事实

- 账号 1128、1129 均为 `apikey` 类型的 OpenAI 外部中转账号，未配置本地代理。
- 错误记录的 `upstream_status_code=403`、`error_owner=provider`、`error_source=upstream_http`；入站为 `/v1/chat/completions`，外部中转实际请求为 `/v1/responses`。
- 18082 将该 403 转为客户端可见的 502 `Upstream access forbidden, please contact administrator`，随后把账号置为临时不可调度。该冷却是保护策略，不是 403 的来源。
- 上游返回文本包含 `Your request was blocked`。因此拒绝发生在外部中转站或它继续转发的更上游链路，而非 18082 的本地权限、余额、并发或 IP 拦截代码。

## 不能仅凭本地日志确认的边界

无法仅据这条 403 区分“外部中转站自身封禁”与“外部中转站的原始供应商拒绝”。可能原因包括：外部 Key 被禁用或额度/套餐权限不匹配、来源 IP/地区/风控策略、请求模型或 `/v1/responses` 端点未授权、并发/RPM 异常触发风控、外部中转站正在屏蔽该 Key。

## 本地策略影响

18082 当前不会主动产生这条 403；本地只会在收到后将账号冷却。因为每个公开 GPT 分组只有一个账号且没有回退，冷却期间才会演变为大量本地 503。解除冷却或降低本地并发可以减少后续无可用账号的 503，但不能修复外部 403。

## 验证方式

向中转站运营方提供发生时间、请求路径 `/v1/responses`、模型和其返回的 403 文案，请其查询该 Key 的拒绝原因。若需自行复现，应使用同一 Key、同一端点和同一模型做最小请求；这会产生外部请求并可能计费，必须在获得运营授权后执行。
