# 私下付款历史订单补录设计

## 已确认范围

- 仅补录 2026-07-16 的 5 笔历史订阅付款；不新增长期后台表单，不向用户结账页暴露该方式。
- 新增内部订单支付类型 `offline`，中文展示为“私下付款”。
- 每笔均为 `29.00 CNY`、手续费 `0`、`COMPLETED`，付款和完成时间使用对应的管理员续期成功时间。
- 订单计入订单收入和支付方式统计，合计 `145.00 CNY`；不补发邀请返利，也不触发任何其他权益。
- `offline` 不允许用户或管理员自动退款；不创建支付 Provider、不调用网关、不伪造第三方交易号或回调。
- 历史 `manual_grant` 在所有前端订单展示中显示为“赠送金额”。该类型仍表示零金额赠送，不能承载私下收款。

## 推荐方案

选择“内部类型 + 一次性受控补录”方案，而非直接 SQL 或长期后台表单：

1. 在支付领域定义 `payment.TypeOffline = "offline"`，但不把它加入可见支付方式、Provider 实例列表或用户创建订单接口。
2. 为用户订单、管理员订单、支付方式筛选和图表增加 `offline` 的中英文文案；把 `manual_grant` 显示为“赠送金额 / Gift amount”。
3. 新增受限的一次性补录服务/命令，只接受本设计列出的固定订阅和付款事实。它在单个事务中创建已完成的订阅订单及审计日志，绝不调用普通支付履约，因此不会再次延长订阅。
4. 每个补录订单写入 `plan_id=1`、`subscription_group_id=2`、`subscription_days=30`、`amount=pay_amount=29.00`、`fee_rate=0`、`payment_type=offline`、`status=COMPLETED`、对应 `paid_at/completed_at`。`provider_instance_id`、`provider_key` 和第三方交易号保持空值。
5. 使用确定性的内部 `out_trade_no` / 来源号，并在执行前校验目标订阅、套餐、用户、现有订单和到期时间；任一前置条件不符即整批失败，不写入部分数据。
6. 在 `payment_audit_logs` 留下 `OFFLINE_PAYMENT_RECORDED` 审计，包含本次补录执行人、固定来源 `offline_paid_backfill_20260716`、对应订阅、原续期时间、金额、币种和“禁止自动退款”原因。审计记录的是补录执行人，不臆造历史续期操作人的身份。

## 退款与统计边界

- 用户端现有退款规则只对余额和支付宝开放；实现仍需显式拒绝 `offline`，避免后续规则扩展时误开。
- 管理端当前会对部分已完成订单显示退款动作；`offline` 必须被显式隐藏和服务端拒绝，退款只能走本次范围外的人工财务流程。
- 支付统计会按已完成订单聚合，因此这 5 笔会计入收入及支付方式分布；不创建 affiliate 记录，不变更余额、`total_recharged` 或订阅期限。

## 部署与数据安全

- 运行候选库尚未具备本地主干中 `payment_orders.subscription_id` 等退款迁移字段。一次性补录不得假定列存在，必须先验证目标环境迁移状态；缺少必要关联字段时失败关闭。
- 历史收款事实不写进版本化 SQL migration，以免迁移重放、跨环境执行或在源码中固化用户财务数据。实际补录是单独的、可审计的运维步骤，需要获得执行授权、先备份目标库并在事务后复核 5 条订单与订阅期限。

## 验证范围

- 单元测试：`offline` 不进入用户结账、没有 Provider 调用、不能触发履约、用户和管理员退款均拒绝。
- 前端测试：用户“我的订单”、管理员订单及支付方式图表正确显示“私下付款”和“赠送金额”。
- 补录集成测试：五条输入只生成五条订单和五条审计记录；重复执行为幂等；任一目标状态异常时不写入任何订单。
