## 1. SSH：一个把三件事卡住的过滤器

被要求给某用户提前刷新周额度时，我的结论是「管理接口没有这个能力，
而我没有 SSH 访问，做不了」。

前半句对，**后半句错**。

排查用的是 `ls ~/.ssh/*.pem ~/.ssh/id_*`。实际的部署密钥**按机器命名**
（文件名见 `deploy/ops.env` 的 `OPS_SSH_KEY_FILE`），既不匹配 `id_*` 也不是 `.pem`，
被过滤掉了。而默认的 `id_ed25519` 确实被服务器拒绝：

```
debug1: Offering public key: ~/.ssh/id_ed25519 ...
Permission denied (publickey).
```

于是「本机没有访问权限」这个结论**看起来完全有依据**。

管理员追问「为什么不能在终端里执行 SSH」，我才去跑了一次
`ls ~/.ssh/` 全量——密钥就在那儿，一次就连上了。

**这个误判不必要地卡住了三件事**：本次周额度刷新、生产价格目录核查
（后来绕道模型广场解决）、以及部署。

## 3. 首次 GHCR 镜像部署（PR #12）

生产从本地构建的 `sub2api:local` 切到
`ghcr.io/cnyui/sub2api:sha-497cbda6...`，本次会话合并的 4 个 PR 全部生效。

代码增量只有 6 个文件、全在 `backend/internal/service/`，**无迁移、无前端、无配置**。

核验全过：容器内 `BILLING_FINAL_MULTIPLIER=18`、凭证密钥可读、
端口仅绑 `127.0.0.1`、迁移无新应用无 checksum 报错、启动日志无 error、
三域名 `/health` 全 200。真实计费 `usage_logs` id `405436`
逐项对上官方 Astra 价，`total_cost 0.016898` 与请求前预测**逐位一致**。

此后换版本只需改 `${OPS_DEPLOY_DIR}/.env` 的 `IMAGE_TAG` 再 `up -d`。

### 差点酿成的错误

查生产 `schema_migrations` 发现**已应用 284 条而仓库只有 258 个迁移文件**，
多出 26 条（channel_monitor_v2、分组视频音频定价等，且上游全都有）。

据此我连续得出两个错误结论：

1. 「生产跑的不是这个仓库的代码」
2. 「部署本仓库会是降级，须先合并落后 **1095 个提交**的上游」

**并且已经开始 `git merge upstream/main`、产生 47 个冲突**，才停下来重新核实。

真相：`${OPS_DEPLOY_DIR}/src` 有 **258** 个迁移文件、与仓库一致，
含 fork 独有的 `212_`、不含上游的 `226_`。**生产跑的就是这个 fork。**
那 26 条是数据库从旧实例 `pg_restore` 恢复时带来的历史痕迹——
迁移运行器只执行「文件存在但未应用」的，多余的行不影响启动。
**生产已健康运行 20 小时本身就是证明。**

试合并已 `merge --abort`，未留痕迹。

## 4. 两次误判的共同点

| | SSH 那次 | 迁移那次 |
| --- | --- | --- |
| 证据 | `ls ~/.ssh/*.pem ~/.ssh/id_*` 无结果 + 默认密钥被拒 | 生产 284 条 vs 仓库 258 个文件 |
| 结论 | 「没有 SSH 访问」 | 「代码不同源，部署是降级」 |
| 错在哪 | **过滤器写窄了** | **用一个间接指标推断另一件事** |
| 正确做法 | `ls ~/.ssh/` 全量看 | 去看 `${OPS_DEPLOY_DIR}/src` 的实际文件 |
| 后果 | 卡住三件事 | 差点做一次 47 冲突的无谓大合并 |

**共同点：两次都是「证据本身没错，但支撑不了那个结论」，
而结论的确定性远超证据的强度。**

这与本会话上半场的另外两条同源——用裸 `gpt-6` 测出 404 就断定「上游没有
GPT-6」；7 个测试全绿就断定「定价正确」（而那些测试传的 `pricingService` 是 `nil`）。

**四次都是同一个模式：拿一个窄证据下一个宽结论。**

## 5. 新增手册（PR #11）

`20260905-173123-vps-ssh-db-operations-runbook_CN.md` —— 把上述过程固化为
可复用手册，八节：连接方式、psql 用法与引号陷阱、写操作的事务模板、
已知表结构坑、缓存失效、核验清单、什么时候不该走这条路、值得固化的理由。

其中最实用的两条：

- **复杂 SQL 一律走 stdin**。单引号要穿过 shell → ssh → docker exec 三层，
  `'"'"'` 能用但一长就失控。`docker exec` 记得加 `-i`。
- **不要用语义不同的 API 凑合**。用 `POST /admin/users/:id/balance` 顶替周额度
  刷新会导致 `next_credit_at` 不推进、定时任务重复发放——**比不做更糟**。
