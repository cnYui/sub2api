# 961109198 Chat Completions 流式 502 根治设计

## 背景

`961109198@qq.com` 的截图附近 502 已定位为应用层错误：`/v1/chat/completions` 流式请求经 `account_id=1/cliproxy-local-openai` 走 Chat Completions 到 Responses 转换后，上游流没有返回计费所需的 terminal usage，Sub2API 返回 `stream usage incomplete: missing terminal event`。用户 Key、订阅、额度、余额、Cloudflare Tunnel、nginx 源站连通性均正常。

这个保护不能删除。缺少 terminal usage 时直接放行 200 会破坏计费准确性；估算 usage 也会制造账务争议。根治点应放在入站协议路由：Chat Completions 客户端应优先走上游 Chat Completions raw 路径，而不是因为账号探测支持 Responses 就被默认转换到 `/v1/responses`。

## 目标

- OpenAI APIKey 账号下，入站 `/v1/chat/completions` 且 body 是标准 Chat Completions shape 时，默认直转上游 `/v1/chat/completions`。
- raw chat 路径继续强制 `stream_options.include_usage=true`，保留“缺 usage 不按成功计费”的保护。
- `/v1/responses` 入站保持现有 Responses 路径，不影响 Codex Desktop、Codex CLI 等正常 Responses 客户端。
- OAuth/ChatGPT 账号保持现有 Chat Completions 到 Responses 转换，因为这类上游依赖 ChatGPT/Codex Responses 链路。
- 手动覆盖继续生效：`force_responses` 强制走 Responses，`force_chat_completions` 强制走 raw chat。

## 非目标

- 不修改用户 `961109198@qq.com` 的 Key、订阅、套餐、额度或余额。
- 不修改数据库运行态账号配置，不重启容器，不发布镜像。
- 不删除 `stream usage incomplete` 保护，不做 usage 估算。
- 不改变正式 API 入口规范：模型 API 仍使用 `/v1/*`。
- 不在本轮重构账号池、failover 策略或 ops 错误表结构。

## 路由设计

采用“入站协议优先”的分流策略：

| 账号类型 | 手动模式 | Body shape | 上游路径 |
| --- | --- | --- | --- |
| OAuth | 任意 | `messages` 或 Responses shape | 现有 CC 到 Responses 路径 |
| APIKey | `force_chat_completions` | 任意 | raw `/v1/chat/completions` |
| APIKey | `force_responses` | 任意 | 现有 CC 到 Responses 路径 |
| APIKey | `auto` 或非法模式 | 有 `messages` | raw `/v1/chat/completions` |
| APIKey | `auto` 或非法模式 | 无 `messages` 且有 `input` | 现有 Responses shape 兼容路径 |
| APIKey | `auto` 或非法模式 | 已探测不支持 Responses | raw `/v1/chat/completions` |

关键点：`openai_responses_supported=true` 仍表示该账号支持 Responses endpoint，但不再等价于“所有 Chat Completions 入站都应转换到 Responses”。Chat shape 由 Chat endpoint 承载，Responses shape 由 Responses endpoint 承载。

## 测试策略

先写失败测试再实现：

1. APIKey 自动模式、探测支持 Responses、标准 Chat Completions body、stream=true，应请求上游 `/v1/chat/completions`，并在上游 body 中看到 `stream_options.include_usage=true`。
2. APIKey 自动模式、未探测、标准 Chat Completions body，应直接请求上游 `/v1/chat/completions`。
3. APIKey `force_responses` 时，标准 Chat Completions body 仍走 `/v1/responses`，prompt cache key 注入保持不变。
4. APIKey 自动模式、Responses shape body 发到 `/v1/chat/completions` URL 时，仍走 `/v1/responses` 兼容分支。
5. `openai_compat` helper 单测覆盖 nil、auto、非法模式、force 两种模式。

## 风险与取舍

- 行为变化会影响 APIKey 账号下所有标准 Chat Completions 入站请求：它们会从“可能 CC 到 Responses”改为 raw chat。这个变化符合协议边界，也能减少 terminal usage 缺失造成的 502。
- `force_responses` 保留给少数必须强制转换的账号，作为可回滚阀门。
- Responses shape 兼容分支保留，避免把带 `input` 的请求误发到 chat endpoint。
- 若某个上游 `/v1/chat/completions` 即使带 `stream_options.include_usage=true` 仍不返回 usage，raw chat 路径会继续按失败处理；这属于上游协议不完整，不能通过账务保护绕过。
