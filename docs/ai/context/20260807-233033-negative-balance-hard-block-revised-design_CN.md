# 负余额硬阻断修订设计

## 对原设计的修订

原设计中的“网关二次预检读取余额缓存或数据库”仍存在旧 Redis 正余额被结算后的异步回填复活问题。最终安全边界改为直接读取 PostgreSQL；Redis 只承担展示和非最终预检加速，不能决定欠费用户是否放行。

API Key 认证快照继续做便宜的负余额早拒绝。主网关、OpenAI 独立入口、Gemini 原生入口、账号等待后的再次检查和 WebSocket 每个 turn 都复用 `CheckBillingEligibility`，从而覆盖长等待、长连接和认证缓存陈旧。

## 结算时序

原有 handler 把 `RecordUsage` 整体提交到 worker 池，导致响应结束、并发槽位释放后资金事务可能尚未提交。此次将用量任务在 handler 内同步执行，统一计费事务完成后才返回；使用日志的 best-effort 写入和余额通知仍允许在服务内部异步处理。

标准模式下，`UsageBillingRepository` 为 nil 时直接返回计费服务不可用，不再调用可透支且不维护套餐子账本的旧 `DeductBalance` 降级路径。Simple 模式仍保持“不计费”的产品语义，但 API Key 认证快照为负时同样拒绝模型执行，避免从标准模式切换期间绕过欠费状态。

## 套餐状态机

`active -> debt_paused` 有两个入口：首周到账后仍为负数；周期任务扫描到仍有后续期数的活动套餐用户已经欠费。暂停不改变 `credited_count`、`next_credit_at` 或 `expires_at`。

`debt_paused -> active` 只能由管理员接口触发，要求余额非负且套餐未到期。恢复时把 `next_credit_at` 设为当前时间，由既有周期任务仅发放一个周额度并重新建立七天节奏；有效期不延长。

`debt_paused -> expired` 由正常到期任务处理。暂停套餐仍属于当前有效套餐，用户可见、可退款，但不能续费或购买其他套餐。

## 批量生图冻结来源

冻结余额若包含余额套餐本周额度，必须在冻结事务中同步减少 `user_balance_packages.remaining_usd`，并在 `batch_image_jobs` 保存套餐 ID 与套餐冻结金额。最终捕获只恢复未消费的套餐部分；取消释放恢复全部套餐部分，但仅在原套餐仍有效时回填子账本。用户总余额的冻结、捕获和释放仍由同一事务维护。

这避免周刷新或到期再次扣除已经被冻结的套餐额度，也避免释放普通充值时错误增加套餐剩余额度。

## 缓存策略

套餐首次到账、周期刷新、到期回收和管理员发放在事务提交后失效用户余额缓存。用量扣费取得 `RETURNING balance` 后，余额低于保底值时同步失效；最终准入始终读取数据库，因此即使缓存失效短暂失败也不会放行欠费请求。

## 剩余边界

OpenAI Live 当前仍缺少完整用量计费实现；本次确保其每次建连前执行数据库欠费终检，但不能把未知费用伪造成扣费。后续需要基于 Live 上游 usage 事件单独实现可审计计费，在此之前应保持现有 `allow_live` 管理开关默认收敛。
