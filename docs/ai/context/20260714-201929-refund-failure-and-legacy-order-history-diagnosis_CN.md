# 退款失败与老用户订单历史缺失诊断

时间：2026-07-14 20:19 JST

## 范围

- 只读核对公网候选库、`sub2api-candidate` 日志、当前退款实现、订单页查询和旧 `yui.web` SQLite 备份。
- 未修改业务代码、PostgreSQL、Redis、支付配置、容器或用户数据。

## 当前退款失败结论

近期明确失败的是 `payment_orders.id=135`：

- 用户：`zhudi189@gmail.com / user_id=67`。
- 原订单：79 元月度套餐，支付宝实付 79.79 元，原支付实例 `provider_instance_id=1 / easypay`。
- 2026-07-14 15:09:00 +08 发起自动退款，按剩余完整天数计算退款 60.60 元。
- ZPay/EasyPay 返回 HTTP 200，但 JSON 业务结果为失败：`卖家余额不足`。
- 服务端正确把订单标记为 `REFUND_FAILED`，首次请求 HTTP 500；当时没有自动撤销订阅。
- 用户 16 秒后重试时，接口因订单已不是 `COMPLETED` 而返回 HTTP 400。
- 2026-07-14 15:13:26 +08，管理员另行调用 `DELETE /api/v1/admin/subscriptions/84` 撤销原订阅；这不是退款流程自动完成的动作。

当前运行库共有 5 个退款结果订单：

- `PARTIALLY_REFUNDED` 2 个。
- `REFUND_FAILED` 3 个。
- 失败原因中 2 个是 ZPay 商户余额不足，1 个是当时 DNS 查询 `zpayz.cn` 失败。

所以本次直接失败点不是用户余额、套餐额度或退款金额算法，而是外部聚合支付商户的可退款余额不足。补足商户余额后仍需管理员重试，因为用户自助接口不允许从 `REFUND_FAILED` 重试。

## 退款实现的结构性风险

当前问题不应只通过“允许失败后再点一次”解决，还存在以下状态模型缺口：

1. `REFUND_FAILED` 混合了不同失败阶段。
   - 网关未退款、网关已退款但撤销订阅失败、余额退款回滚失败可能落到相同或相近状态。
   - 管理员重试允许处理 `REFUND_FAILED`，但代码不能可靠判断是否已经发生真实资金退款，存在重复退款风险。
2. 支付宝自动退款是“先网关退款，再撤销订阅”。
   - 如果网关退款成功、撤销订阅失败，订单会被标记为 `REFUND_FAILED`。
   - 后续重试可能再次调用支付网关，不能把这种情况当作普通可重试失败。
3. 通用退款响应把 `pending` 当作成功。
   - 异步退款仍在处理中就可能撤销权益并最终标记退款成功，缺少退款结果查询和对账阶段。
4. `payment_trade_no` 为空时，`gwRefund()` 写审计后直接返回成功。
   - 这可能导致没有实际发起网关退款却撤销订阅并标记成功。
5. 订单没有持久化关联准确的 `user_subscriptions.id`。
   - 退款时按 `user_id + group_id` 查当前 active subscription，而不是查该订单实际发放的权益。
   - 当前通过 `user_subscriptions.notes = "payment order <id>"` 保留弱关联，不适合作为财务状态机依据。

## 老用户订单页缺失根因

用户订单页 `GET /api/v1/payment/orders/my` 只查询 `payment_orders`，不会读取：

- `user_subscriptions`；
- `redeem_codes`；
- 管理员手工分配记录；
- 旧 `yui.web` SQLite 的购买订单。

运行态数据规模：

- `payment_orders` 共 178 条，最早创建于 2026-06-26，覆盖 82 个用户。
- `user_subscriptions` 共 89 条，最早创建于 2026-06-18，覆盖 72 个用户。
- 其中 44 条订阅完全没有当前支付订单来源，涉及 38 个用户，当前仍有效 32 条；另有 1 条仍保留订单号，但 notes 被管理员追加了修复说明，说明字符串关联本身不可靠。
- 这 44 条包括：15 条旧 `yui.web` 迁移、17 条兑换码、7 条人工分配、4 条空备注人工/系统分配，以及 1 条其他修复记录。它们不能全部等同于“已支付订单”。

旧 SQLite 备份仍保留可核验来源：

- `orders`：15 条旧 Key/套餐交付记录，金额、交付时间和到期时间完整。
- `subscription_orders`：13 条，其中 10 条 `LEGACY-SUB-*` 是迁移时生成的存量订阅镜像，不是新的独立付款；另外 3 条是实际人工确认的订阅订单。
- `subscription_refund_requests`：1 条已批准退款记录。
- 2026-06-18 的迁移脚本只迁移了 API Key、订阅权益和用量，没有把旧购买订单迁入 `payment_orders`。

因此旧历史不是前端漏显示，也不是数据完全丢失，而是购买事实仍留在旧库，当前订单读模型没有导入。

## 候选优化方案

### 方案一：扩展 `payment_orders` 并做有来源的幂等回填（推荐）

- 给订单增加 `source_system`、`source_order_id`、`refund_mode`、`subscription_id` 等明确字段。
- 当前新订单标记为原生订单；旧记录按旧库主键回填，建立唯一约束，保证脚本可重复执行。
- 排除 `LEGACY-SUB-*` 这类迁移镜像，避免与旧 `orders` 重复计算购买历史。
- 已有旧退款记录映射为退款完成状态；无法证明支付渠道交易号的历史订单只允许“申请人工退款”，禁止自动调用网关。
- 新订单履约时直接写入准确的 `subscription_id`，逐步淘汰 notes 字符串关联。

优点是继续复用现有订单页、分页、管理后台和审计体系。风险是必须同步修正收入统计、退款资格和迁移去重规则，不能简单插入 `COMPLETED` 行。

### 方案二：新增独立的历史购买表和统一订单读模型

- 旧订单写入不可变 `legacy_purchase_records`。
- 订单 API 联合当前订单与历史购买记录，退款接口按来源分流。

边界更干净，但前后端分页、筛选、ID、管理后台和退款入口都要支持联合模型，改动明显更大。

### 方案三：订单页直接合并订阅、兑换码和人工分配记录（不推荐）

实现最快，但会把“权益来源”误当成“付款订单”，无法证明金额、支付渠道和是否已退款，容易产生错误退款和财务统计污染。

## 推荐方向

采用方案一，但将退款状态机和历史回填拆成两个阶段：

1. 先修退款状态机：区分网关未退款、退款处理中、网关已退款待撤权、最终失败；补充幂等键和退款结果核验。
2. 再回填老订单：只导入有原始购买证据的记录，标记来源和人工退款模式；兑换码、赠送、管理员直加只展示为权益记录，不伪造成支付订单。

需要业务确认的唯一关键口径：老订单是否接受“用户提交申请、管理员核验后线下退款”，还是要求自动原路退。现有旧库没有支付宝/微信网关交易号，后者无法在不补充外部支付凭证的前提下可靠实现。
