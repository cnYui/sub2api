# 三个 GPT 渠道状态接入记录

## 目标

将以下公开渠道展示到用户侧 `/monitor`，且不重建、不重启或修改公网 `18082` 容器：

- GPT模型官方0.35倍稳定
- GPT0模型官方0.1倍低价不稳定
- GPT-Image-2生图

密钥仅通过本机管理接口或上游认证请求使用，不写入仓库、本文档或运行日志。

## 实施与结果

1. 通过现有管理接口创建了两个文本渠道监控，服务端完成凭证加密并立即加入运行中的调度器：
   - `channel_monitors.id=8`：`GPT模型官方0.35倍稳定监控`，主模型 `gpt-5.6-sol`。
   - `channel_monitors.id=9`：`GPT0模型官方0.1倍低价不稳定监控`，主模型 `gpt-5.5`。
   - 两者均为 OpenAI Chat Completions 协议、上游 `https://api.ai-genesis.app`、60 秒间隔。
2. 两个文本渠道的首次自动检测均为 `operational`，并已在用户接口中返回。
3. 图像模型不能用聊天探测替代：当前线上监控器仅支持 Chat Completions 与 Responses；以 `gpt-image-2` 发送文本探测会产生协议错误，而图像生成探测会反复产生生图费用。
4. 因此对 `gpt-image-2` 执行了一次已认证的 `GET /v1/models` 校验。上游返回 HTTP 200，模型目录包含 `gpt-image-2`，耗时 719ms，未请求或生成图片。
5. 该事实状态已写入 `channel_monitors.id=10`（`GPT-Image-2生图监控`）并展示给用户，首条历史为 `operational`、可用率 100%。

## 当前限制

图像渠道的这条状态是一次性模型目录校验，不是当前线上版本的持续轮询。为确保不影响公网 `18082`，本次没有部署“模型目录探测”协议，也没有重启容器；记录在创建时未加入当前进程的调度器。

后续若需要持续、无生图费用的图像渠道监控，应先在代码中增加 OpenAI `GET /v1/models` 探测模式，完成测试后随正常发布部署，再将该监控切换到新协议。不得用聊天请求伪测图像模型，也不得按分钟生成图片作为健康检查。

## 验证

认证用户接口 `GET /api/v1/channel-monitors` 已返回三个新增项目：

- `GPT模型官方0.35倍稳定监控`：首次为 `operational`；最新一次为 `degraded`，响应 7512ms，原因是超过 6 秒慢响应阈值，7 天可用率仍为 100%。
- `GPT0模型官方0.1倍低价不稳定监控`：最新为 `operational`，响应 2121ms，7 天可用率 100%。
- `GPT-Image-2生图监控`：`gpt-image-2`，`operational`，7 天可用率 100%。

容器保持原实例运行，`http://127.0.0.1:18082/health` 返回 200。
